## 5. SDR / BDR 特有の確認

### 5-1. 既存「インサイドセールス」ユーザー

**現状 1名** が `job_type = "インサイドセールス"` で登録済み。

SDR/BDR を追加した場合、この1名の扱いが問題になる。選択肢は3つ:

| 選択肢 | 内容 | メリット | デメリット |
|-------|------|--------|----------|
| **A. インサイドセールスを残す（推奨）** | SDR/BDR を追加しつつ、インサイドセールスもJOB_TYPESに残す | 既存ユーザーへの影響ゼロ。将来のユーザーは3つから選べる | SDR/BDR/インサイドセールスが並立し、選択肢として似通う |
| **B. インサイドセールスをlegacy扱いにする** | JOB_TYPESのインサイドセールスをlegacy末尾に移動、P1カテゴリでは非表示。新規ユーザーにはSDR/BDRを提示 | 新規には整理されたUI | 既存1名は古い値のまま残る（実害は特になし） |
| **C. 既存ユーザーをSOR/BDRに移行する** | SQL UPDATE でインサイドセールス → SDR or BDR に書き換え | DB値を統一できる | 本人に確認なしで職種を変えることになる。1名なので聞いてから移行が現実的 |

**推奨: 選択肢A（インサイドセールスを残す）**

理由:
- 現在は4名しか設定済みユーザーがいない。インサイドセールスのユーザーは1名
- SDR/BDR という概念が普及する前にオンボーディングしたユーザーが自然に発生する
- JOB_TYPESに3つ並んでも実害はない。P1の2段階UI（カテゴリ→サブ選択）で整理できる

### 5-2. 日本 SaaS 文脈での SDR/BDR 粒度の需要

**現状の判断材料:**
- `ow_jobs` の `job_category` にはSDR/BDR相当の職種が含まれていない（インサイドセールス, セールス 等）
- Salesforce の求人106件（migration 166）の job_category に "インサイドセールス" が存在（queries.ts:693）
- `/biz/candidates` フィルタは企業が候補者を絞る用途。SDR/BDRで絞りたいニーズが企業側にあるかどうか

**評価:**
- SDR/BDRという用語は国内SaaS業界（HubSpot, Salesforce, SmartHR系）では定着している
- 一方、求職者がSDR/BDRで自己識別するかは文脈依存。「インサイドセールス（SDR）」のように補足表記が親切
- **フィルタ需要:** 現状4名のみ。データが少なすぎて判断不能。実ユーザーが増えてから導入する方が合理的

## 6. 企業フィルタ（/biz/candidates）空振りリスク評価

```typescript
// CandidatesClient.tsx:76
if (jobType) list = list.filter((c) => c.jobType === jobType);
```

**完全一致のクライアントサイドフィルタ。**

フィルタの選択肢 = `JOB_TYPE_OPTIONS = [...JOB_TYPES]`

→ **新職種を JOB_TYPES に追加した瞬間、フィルタ選択肢にも自動で現れ、一致ロジックも自動で動く。**

「フィルタに出るが必ず0件」（空振り）の構造的リスクは存在しない。
ただし、現状はユーザーが4名しかいないため、どの職種フィルタも0件になる可能性が高い。これはデータ不足の問題であり、フィルタロジックの問題ではない。

## 8. セールス・CS カテゴリ 追加後の職種構成

### 現状（3職種）

```
セールス・CS
├── フィールドセールス
├── インサイドセールス
└── カスタマーサクセス
```

### 追加案A: 4職種追加、インサイドセールスを残す（推奨）

```
セールス・CS
├── フィールドセールス
├── SDR（または SDR（新規開拓））
├── BDR（または BDR（戦略開拓））
├── インサイドセールス        ← legacy扱い or 汎用として残す
├── カスタマーサクセス
└── カスタマーサポート
```

**6職種。** エンジニアリング（6職種）と同数なのでカテゴリUIとして問題ない。
ただし SDR/BDR/インサイドセールスが3並列するのは「重なって見える」可能性あり。

### 追加案B: インサイドセールスをlegacy移動、4職種のみ追加

```
セールス・CS
├── フィールドセールス
├── SDR
├── BDR
├── カスタマーサクセス
└── カスタマーサポート
```

**5職種。** スッキリするが、既存「インサイドセールス」ユーザーへの配慮が必要。

### 追加案C: SDR/BDRは今回見送り、カスタマーサポートとPMMのみ追加

```
セールス・CS
├── フィールドセールス
├── インサイドセールス
├── カスタマーサクセス
└── カスタマーサポート        ← 今回追加

マーケ・コーポレート
├── マーケティング
├── プロダクトマーケティング  ← 今回追加
├── コーポレート
├── HR・人事
├── 財務・経理
└── 事業開発・BizDev
```

SDR/BDRは実ユーザーが増えてから判断。

## 9. 全体影響まとめ

### 4職種追加で必要な作業（全て）

```
1. src/lib/constants/jobTypes.ts — JOB_TYPES 配列に4値を追加（4行）
   ※ 追加場所はカテゴリコメントに合わせて適切な位置に挿入

2. docs/research-onboarding-p1-2step-2026-07.md の JOB_TYPE_CATEGORIES 案を更新
   （セールス・CS の types[] に新職種を追加）
```

**それ以外の変更はゼロ。**

| 変更が不要な理由 |
|----------------|
| DB は TEXT 自由文字列、CHECK 制約なし → マイグレーション不要 |
| 全レイヤーで変換テーブルなし → 変換漏れが起きる構造自体がない |

| 公開プロフィール（/u/[id]）は job_type 非表示 → 影響なし |

### 唯一の「要検討」事項

**SDR/BDR とインサイドセールスの共存方針**（§5参照）。
DB移行は不要だが、P1の2段階UIでカテゴリ内の職種並びをどう整理するか（案A/B/C）は柴さんの判断が必要。
