## 障害記録：ow_experiences.why 本番500（2026-05-19 / クローズ済み）

### 障害
本番 opinio.jp で職歴の保存・取得が全面的に500エラー。
レスポンス: {"error":"column ow_experiences.why does not exist"}
影響範囲：/profile/edit の職歴 新規作成・取得・編集すべて。
ユーザーには「職歴はまだ登録されていません」「追加に失敗しました」と表示されていた。

### 原因
ow_experiences.why カラムを削除する migration が DB に先行適用されていた一方、
コード側は why を INSERT/SELECT/UPDATE/表示で参照したままだった。
DBとコードの不整合により、職歴系APIが500で全面停止。
本質：カラム削除を expand-contract の逆順で実施したことによる本番障害。

### 対応（前進復旧：DBを正としコードをwhy非依存に修正）
- STEP 1 棚卸し：grep -rn "\bwhy\b" src/ で全why参照を分類。
  「対象7ファイル」「除外2ファイル（記事スラッグ誤マッチ）」以外の
  実フィールドwhy = 0件 であることを確認。
- 除外（変更せず）：src/app/articles/mockArticleData.ts /
  src/app/mypage/mockMypageData.ts（"layerx-nakamura-why-mentor" 誤マッチ）
- 修正：対象7ファイルから why を完全除去
  - src/app/api/jobseeker/experiences/route.ts（SELECT/レスポンス/POST payload）
  - src/app/api/jobseeker/experiences/[id]/route.ts（更新 payload）
  - src/app/(jobseeker)/u/[id]/page.tsx（SELECT）
  - src/app/(jobseeker)/mypage/page.tsx（SELECT）
  - src/lib/utils/career.ts（型定義）
  - src/components/profile/CareerHistoryEditor.tsx（型/state/フォームUI/全保存payload）
  - src/components/profile/CareerTimeline.tsx（表示ブロック）
- コミット：fecd452 "fix: remove ow_experiences.why from all code paths (本番500復旧)"

### 検証（2026-05-19 本番実機で確認・全パス成功）
- 職歴 新規作成：POST 201 成功
- 職歴 既存編集→保存：「職歴を更新しました」成功（更新APIも正常）
- 表示面（職歴一覧／タイムライン／公開プロフィール u/[id]）：why欄削除後も崩れなし
- Network上に新規500なし。障害解消を確認しクローズ。

### 再発防止ルール（重要・恒久ルール化）
カラム削除（column drop）は必ず expand-contract を順守する：
  ① コードから当該カラムの参照を完全除去 → デプロイ
  ② 本番が ● Ready であることを commit hash で確認
  ③ ②の確認後に、後追いで migration による column drop を実施
**逆順（DB先行drop → コード後追い）は本番全面停止を招くため厳禁。**
DB変更とコード変更を別デプロイに分ける場合は特にこの順序を厳守すること。
このルールは既存の運用ルール（npm run build → git push origin main →
Vercel ● Ready 確認）に並ぶ恒久ルールとして扱う。

### 1. OB・OGカードを現役社員カードと配色統一・ALUMNIバッジ削除
- **commit**: 9dcdc8d
- **対象**: src/app/(jobseeker)/companies/[id]/page.tsx の AlumniCard
- **背景**: hover時に背景が濃色→白に変わるが、文字色（#fff/#B5D4F4）が
  反転せず白背景に白文字で読めなくなる不具合
- **方針**: 共通の .employee-card-link:hover を直接変えると現役社員カードを
  巻き込むため、AlumniCardの配色そのものをEmployeeCardと統一する方式に。
  hover問題は配色統一の副次効果で自動解消
- **変更**: 背景#042C53→var(--bg-tint)、文字#fff→var(--ink)、
  役職#B5D4F4→var(--ink-soft)、退職テキスト→var(--ink-mute)、
  アバターをresolveAvatarColor()+avatarInitialに（EmployeeCardと同形式）、
  ALUMNIバッジ削除（OB・OGセクション内なので冗長）
- **学び**: 共通クラスを安易に変更しない。配色を揃えれば hover も自動的に
  整う。AlumniCardの配色がほぼ全てハードコード（#042C53等）だったのが
  事故の温床だったため、デザイントークン化で予防にもつながった

## 共通の方針・恒久ルール（再発防止と作業効率の知見）

5/19 の作業を通じて確立した、ソロ＋Claude Code 体制での作業ルール：

### スキーマ変更とコード変更の順序（再掲・最重要）
カラム削除（column drop）は必ず expand-contract を順守：
  ① コードから参照除去をデプロイ
  ② 本番が ● Ready になることを commit hash で確認
  ③ ②の確認後に migration による column drop を実施
逆順厳禁。

### Claude Code への作業指示の標準パターン
1. **調査だけ先行**：read-only の調査指示を投げ、対象ファイル・該当行・
   共有コンポーネントの有無・既存トークン・ハードコード値を把握
2. **方針を人間が決める**：調査結果を見てから、案を複数出して選ぶ
3. **最小スコープで指示**：行番号・変更箇所・触らない箇所を明示。
   特に「触らないこと」のリストが事故防止に効く
4. **実機検証まで閉じる**：build→push→Vercel Ready→本番実機で確認、
   までを1セット。ビルド通過は「直った」ではない

### テストデータに引っ張られない判断
- テストデータで「重複・冗長に見える」要素が、実データでは別情報の
  ケースがある（5/19 の roleTitle、logo_url が良例）
- 「これは本当に問題か、テストデータ固有の見た目か」を都度確認
- 存在しない問題のための実装は避ける

### 共通コンポーネントを触る時のリスク管理
- 共有クラス/共有定数を直接変更すると別ページを巻き込む
  （5/19 の .employee-card-link:hover、EMPLOYEE_GRID_STYLE が該当）
- 対策：①個別側を共通に合わせる、②上書きで対応、③専用クラスに分離、
  のいずれかでスコープを限定

### 配色のデザイントークン化（バックログ候補）
/companies/[id] 配下を中心に、まだハードコード値（#042C53、#fff 等）が
残っている可能性。今後の hover/可読性事故の予防として、配色のデザイン
トークン統一は順次進める価値あり。優先度は低めの恒常リファクタ。
