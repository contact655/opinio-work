## avatar_color / cover_color に値の検証が無い（2026-08-15 記録）

**対象**: `PUT /api/jobseeker/profile` の `avatar_color` / `cover_color`

**やるなら**: 既定のグラデーション一覧をホワイトリストにして、外れた値は **400**

UI と API が同じ定数を見る（CLAUDE.md「UI / API / DB の CHECK を3つ揃える」）。

## プロフィール画像・カバーに圧縮 / リサイズ / サイズ上限が無い（2026-08-15 記録）

**対象**: `/profile/edit` のアップロード（`ProfileEditClient.tsx` の `uploadPhoto`）。
バケットは `ow-uploads`、パスは `users/{avatars|covers}/{owUserId}/{Date.now()}.{ext}`。

**なぜ残っているか**: クライアントが `File` をそのまま `supabase.storage.upload` に渡しており、
**圧縮・リサイズがコード上に1つも無い**。スマホで撮った数MBの写真がそのまま公開プロフィールに載る。

⚠️ **サイズ上限は「無い」ではなく「バケット側にある」**（2026-08-15 実測で訂正）。
   `ow-uploads` は `file_size_limit = 5 MiB`、`allowed_mime_types` は jpeg/png/webp/gif。
   超えるとアップロードは失敗するが、**画面には何も出ない**のが問題。

**やるなら**: アップロード前にクライアントで長辺をリサイズ（Canvas か `createImageBitmap`）し、
上限（例: 5MB）を超えるものは弾く。**弾いたことを画面に出す**（黙って落とさない）。

## `social_links` の空文字がキーごと残る（2026-08-15 記録）

**対象**: `PUT /api/jobseeker/profile` の `social_links`（`ow_users.social_links` / JSONB）。

**なぜ残っているか**: 2026-08-15 に空入力を null へ寄せた（`lib/api/normalize.ts`）が、
対象は **text 列だけ**で JSONB は素通し（`patch.social_links = body.social_links as Json | null`）。
SNS の入力を空にして保存すると `null` ではなく **`{"x": ""}`** が残る（実測）。
表示側は truthy 判定なので画面は無事だが、キー存在判定（`social_links ? 'x'`）や
充填率の集計は誤る。

**やるなら**: 空文字の値を持つキーを落とし、全キーが空になったら列ごと null にする。
正規化は `normalize.ts` に足し、`profile/route.ts` がそれを通る形にする
（route に if を書き足さない）。既存データの掃除は**別コミットの migration**。

## social_links に URL 形式の検証が無い（2026-08-16 記録・未着手）

**空の扱いは `optionalTextMap` で揃った（2026-08-16）が、形式は見ていない。**
実データに **`github: "a"`** のような値が入っている（`ow_users` 1行）。

`content-links` 側は **https 必須**の検証があるのに、`social_links` には無い。
**同じ「外部リンク」なのに扱いが揃っていない。**

### ★実装する前に決めること（ここが本題）

⚠️ **素直に 400 を返すと、過去の壊れた値のせいで「名前の変更すら保存できない」状態になる。**
`social_links` は `PUT /api/jobseeker/profile` に**他の項目と一緒に載る**ため、
1つでも不正な値が残っていると、そのユーザーは基本情報カードを保存できなくなる。

先に3択を決めること。

| 案 | 中身 | 引っかかる点 |
|---|---|---|
| A | **変更されたキーだけ検証する** | 保存は通る。壊れた値は**残り続ける**。「送られてこなかったキー」を保持する実装が要る（いまは丸ごと置き換え） |
| B | **保存時に壊れた値を落とす** | 自動で綺麗になるが、**利用者に断りなく消える**。「値が無いことを、ある値に置き換えない」の裏返しで、**入力したものを黙って消す**ことになる |
| C | **UI 側で該当欄に印を出して直させる** | 筋は通るが、**保存を止めるかどうかは別途決める**（止めるなら A と同じ問題が出る） |

★**壊れた行が現在1件しかないなら、先にデータを直せば「素直に400」が安全になる。**
過去の値が保存を塞ぐのは「過去の値が壊れている」から起きるので、**0件にしてから
厳格な検証を入れれば、案Aの「変更されたキーだけ検証する」実装も案Cの印も要らなくなる。**
案B（黙って落とす）は「値が無いことを、ある値に置き換えない」の裏返しなので**採らない**。

⚠️ **あわせて「UI / API / DB の CHECK をどこまで揃えるか」も決める**（CLAUDE.md の原則）。
   `social_links` は JSONB なので、DB 側で形式を縛るなら CHECK 制約の書き方から要検討。
   縛らないなら「縛らないと決めた」ことを書き残すこと。

⚠️ 参考: `content-links` の検証は `POST/PUT /api/jobseeker/content-links` にあり、
   `error` は識別子・`message` は画面用に揃えてある（2026-08-16）。文言の形はここに倣う。

## モバイル（767px 以下）で公開促進が見えない（2026-08-16 記録・未着手）

`MypageLayout` は **767px 以下で左右どちらの `aside` も `display:none`** にする。

判断の経緯: 表示コードは全部そろっていて `future={null}` で殺されているだけだった。
「入力できるのに誰にも届かない欄」を残すほうが害が大きいと判断して出す側に倒した。

⚠️ **内側ナビ（自己紹介 / 職歴 / 学歴 / 実績 / 発信）には項目を足していない。**
   足さなくても破綻しない。足すかどうかは別判断。
