## 複数ポジション機能の実装（CareerHistoryEditor のみ対応）

### 背景

柴さんから「1社で複数ポジションを経験している場合（例：セールスフォースで
IS→FS）の実装をお願いしたい」という相談。データモデル設計から UI/UX まで
一連で実装した。

### データモデル調査（着手前の事実確認）

「〜のはず」で進めないため、SQL で現状を確定してから設計に入った。

`ow_experiences` のスキーマ確認：
- 14カラム（id / user_id / company_id / company_text / company_anonymized /
  role_category_id / role_title / started_at / ended_at / is_current /
  description / display_order / created_at / updated_at）
- **UNIQUE 制約なし**（CHECK / FK / PK のみ。複数行登録は DB レベルで完全許可）
- **CHECK 制約 `experience_company_xor`**：`company_id` / `company_text` /
  `company_anonymized` の3者排他（必ず1つだけ NOT NULL）

調査結果：migration 不要、API 変更不要、`/profile/edit` の UI 改修のみで完結。

### 案A改 vs 案B の判断

柴さんは当初「案B：フォーム入れ子化」を希望したが、コードを読んだ上で
**案A改**（表示集約 + 入力プリフィル、データ構造変更なし）を推奨。

案A改を選んだ理由：
1. 内部データ構造・API はゼロ変更（リスク最小）
2. ユーザー体験として「同じ会社で複数ポジション」の課題はほぼ完全に解決
3. 案Bは内部状態の再設計を伴い、1セッションで完結困難
4. 「会社情報を1箇所で持って同期させる」需要は現時点で存在しない

### 実装内容（commit 47e301e）

`src/components/profile/CareerHistoryEditor.tsx` に以下を追加：

```typescript
type StintGroup = { key, companyType, companyId?, companyText?, ...,
                    positions, earliestStart, latestEnd, totalMonths }

function groupStints(stints: Stint[]): StintGroup[]
function diffInMonths(startYM, endYM): number
function formatDuration(months): string
function formatGroupPeriod(group): string
```

グループ化キー方針：
- master → `m:${companyId}`
- custom → `c:${companyText}`（文字列一致でグループ化）
- anon → `a:${companyAnonymized || displayCompanyName}`

UI 変更：
- `stints.map` → `groupStints(stints).map`
- グループヘッダー（会社名 + 在籍期間 · X年Yヶ月）
- `adding: boolean` → `addingForCompanyKey: string | null`（プリフィル制御用）
- StintForm に `companyLocked` prop 追加（グループ内追加時は会社名 disabled）
- `draftFromGroup()` 関数追加（グループから company 情報をプリフィルする）
- `StintCard` から会社名表示を削除（グループヘッダーに統合）

変更規模：+234行 / -45行（1ファイルのみ）。
Map イテレーションで TypeScript ターゲット設定の制約に遭遇し `Array.from(map)` で回避。

## 明日以降の課題：MergedTimeline 横断対応プロジェクト

### 課題の本質

`MergedTimeline.tsx` で経歴を会社単位でグループ化する機能を実装する。
同時に、`CareerHistoryEditor` の `groupStints()` ロジックとの整合性を取る。

### 設計判断ポイント（明日着手前に確定）

1. **共通化アプローチ**
   - パターンA：`career.ts` に `groupExperiencesByCompany()` を追加して両者で共有
   - パターンB：`CareerHistoryEditor` の `groupStints()` をそのまま `career.ts` に移動
   - パターンC：MergedTimeline 内で独自実装（重複容認）
   - **推奨はA**：CareerEntry 型を統一見られる、最も綺麗

2. **Stint 型と CareerEntry 型の関係**
   - 現状は別物（CareerHistoryEditor は Stint、MergedTimeline は CareerEntry）
   - 統合するか、別管理のまま共通関数だけ作るかの判断
   - **推奨は別管理**：型の役割が違うため、無理に統合しない

3. **既存の `groupOverlappingCareers()` との整理**
   - 既存関数は「期間重なりでグループ化」（並行職用）
   - 今回追加するのは「同社でグループ化」（昇進・異動用）
   - 両者は共存させる（用途が違う）
   - 関数名を `groupBySameCompany()` のような明確な命名に

4. **タイムラインUIのレイアウト変更**
   - スクショ1で見た縦線タイムライン UI が、グループ化後にどう見えるか
   - 同社の複数ポジションを「会社ヘッダー1つ + ぶら下がるポジション複数」で
     表現すると、タイムラインの「年月ラベル」がどこに付くかが論点
   - MergedTimeline.tsx を読まないと確定できない

### 明日のセッション開始時の手順

1. `MergedTimeline.tsx` の全文を読む（必須）
2. `/u/[id]/page.tsx` の経歴データ取得部分を読む（SSR でどう渡しているか）
3. 上記4つの設計判断ポイントを確定
4. `career.ts` に `groupBySameCompany()` を追加（共通関数）
5. `MergedTimeline.tsx` で同社グループ化表示を実装
6. `CareerHistoryEditor.tsx` の `groupStints()` を `career.ts` の共通関数に
   置き換え（リファクタリング）
7. 動作確認：`/profile/edit` / `/mypage` / `/u/[id]` の3画面で同じデータが
   同じグループ化ロジックで表示されることを確認

### 想定スコープ

- 1セッションで完結可能（中規模、推定3〜4時間）
- 影響ファイル：3〜4ファイル
- 動作確認も3画面分

## 今日の学び（恒久ルール候補）

### SQL 確認は早めに（前提条件チェック）

`ow_experiences` の UNIQUE 制約・XOR 制約・カラム構造を SQL で確認してから
設計に入った。migration が必要かもしれない不確実性を10秒で解消できた。

### grep の範囲は広めに、初回調査こそ慎重に

最初に「経歴表示画面が存在しない」と早合点したのが今日最大の反省点。
grep 範囲を `src/app/(jobseeker)/profile/` 配下に限定したため、
`MergedTimeline` を見逃した。**最初の調査こそ広範囲に**を恒久ルール候補に。

具体的な推奨手順：
- ow_experiences など主要テーブル名を src/ 全体で grep
- 共通コンポーネント候補は `src/components/` 配下も明示的に確認
- 関連ユーティリティは `src/lib/utils/` を必ず確認

### デザイン判断は「実用シーン」で検証する

案① → 案② の最終ピボットは、「1社だけのモックで見ていた時には案①が良く
見えた」が、「複数社並んだモックを描いて初めて案②の優位が見えた」という経過。
Visualizer ツールでの3〜5社並びモック表示が決定打。

### 判断疲労を見越して「freeze」を提案する

デザイン判断が5回変わったタイミングで一度ブレーキを踏み、「判断疲労からの変更か、
新しい情報に基づく判断か」を言語化してから進めた。

### コードを読んで設計修正することを恐れない

複数ポジション機能の実装時、当初の「案B」から「案A改」に設計を1段階軽量化した。
コードを読んだ上で初めて見えた事実で方針を変えるのは正しい姿勢。

### セッション終盤の新発見は明日に回す

今日の MergedTimeline 発見は、本来なら朝の調査で見つかっているべきだったもの。
セッション7〜8時間目で見つかった発見を、その日のうちに対処しようとするのは
品質リスクが極めて高い。**「明日のためのアセット」として記録する**ことを選んだ。
