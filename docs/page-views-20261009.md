# 閲覧数の記録と /biz/analytics（2026-10-09 / 段階D）

## 何を作ったか

| | 実体 |
|---|---|
| 表 | `ow_page_view_daily`（日付 × ページ種別 × ページ id → 件数）。**閲覧者の ID を持たない** |
| 増やす | `increment_page_view()`（service_role だけ実行できる） |
| 記録の入口 | `POST /api/views`（ページの `ViewBeacon` が開いたときに1回呼ぶ） |
| 判定 | `lib/views/decide.ts` の `decideView()`（純粋な関数） |
| 1日1回 | cookie `ov`（今日の日付と、数えたページの短い鍵だけ。ランダムな ID を入れない） |
| 表示 | `/biz/analytics` の「閲覧数」（企業ページ・求人の合計、日ごと／月ごとの推移）と「求人ごとの反応」の「閲覧」列 |

権限は `ow_transitions` と同じ形（RLS 有効・ポリシー0本・anon / authenticated に GRANT 無し）。
実測（2026-10-09）: anon・ログイン中の人とも、表の読み取りと関数の実行が 401 / 403。

### 除くもの

検証用（is_test）・システム（is_system）・運営（auth_is_admin）・その企業の有効な担当者・ロボット（User-Agent）・
公開されていないページ・同じブラウザで今日すでに数えたページ。

⚠️ 自分の `ow_users` 行が引けないログイン中の人は**数えない**側に倒している。

### 開発環境では書かない

dev も本番の DB に繋がっているので、`NODE_ENV !== "production"` では書かずに判定結果だけ返す
（`{ counted, reason, devNoWrite: true }`）。書きたいときだけ `VIEW_RECORD_IN_DEV=true`。
⚠️ `next start`（ローカル本番ビルド）とプレビューデプロイは書く。

## 検証用でない閲覧として数えられることを、どう確かめたか

検証用アカウントの `is_test` を外さずに確かめるため、判定を純粋な関数にしてある。

1. `decideView()` に**作り物の閲覧者**（is_test=false・運営でも担当者でもない）を渡すと `count` になる。
   ほかの8通り（未ログイン・検証用・システム・運営・担当者・今日すでに数えた・ロボット・非公開）も期待どおり（9/9）
2. dev の `POST /api/views` を叩き、未ログイン → 数える、2回目（cookie あり）→ `seen_today`、
   ロボット → `bot`、非公開の企業 → `not_public`、検証用アカウント → `test_account`。dev では行が増えない（0 → 0）
3. 書き込みの陽性対照は service_role で `increment_page_view()` を2回呼んで 2 になることを確かめ、消した

⚠️ 運営・担当者を除く分岐は、実在する検証用アカウントがどれも is_test で先に除かれるので、**画面からは通せない**。
   1.（純粋な関数）でだけ確かめている。

### 閲覧した人の属性の内訳（プライバシーポリシーの改定の後）

- 例: 職種（大分類）・社会人年数の帯・転職意欲の内訳を、期間ごとに出す
- 形の案: `ow_page_view_daily` とは**別の表**に、日 × ページ × 属性の値 → 件数で持つ（閲覧者 ID は持たない）
- ⚠️ 少人数だと誰か分かる。**k 件未満の区分は出さない**（例: 5 未満は「その他」に畳む）
- ⚠️ ログイン中の人の属性をページの閲覧に結びつけることになるので、**プライバシーポリシーの改定が先**
- ⚠️ 年齢・性別では作らない（企業に絞り込み・内訳の手段を渡さない方針）

### 閲覧から面談申込・応募・保存へ進んだ割合

- 素直な形（閲覧した人のうち何人が申し込んだか）は、**閲覧者の ID を残さない方針と両立しない**
- 代わりの案: 期間ごとの「閲覧数」と「申込・応募・保存の数」を並べ、**比（件数 ÷ 閲覧数）**として出す。
  同じ人を追わないので「割合」ではなく「閲覧あたりの件数」と書く
- ⚠️ 閲覧の記録は 2026-10-09 から。それより前の申込・応募と割ると比が大きく出るので、期間を記録開始以降に揃える
