# /admin の中身が、運営でないアカウントに RSC で渡っていた（2026-10-10）

## 何が起きていたか

`/admin/layout.tsx` は運営でなければ「この画面は運営メンバーだけが開けます」を返すが、
**ページ側のサーバーコンポーネントは並行して実行され、その結果が RSC ペイロード（HTML 内の `self.__next_f`）に載っていた。**

実測（2026-10-10 / 本番 opinio.jp）: 運営でない検証用アカウント（contact+15）で `/admin/plans` を開くと、
画面は権限エラーなのに、HTML に**企業名とプランの一覧**が入っていた。dev でも同じ（`/admin/approach-range` も同じ形）。
未ログインは middleware が `/auth` へ飛ばすので漏れていない。漏れていたのは「ログインしている、運営でない人」。

## 直し方

`src/middleware.ts` で、`/admin` 配下はログイン済みでも**運営でなければ 403**（`/no-admin-access` へ書き換え）。
判定は `ow_user_roles` に `role='admin'`（`auth_is_admin()` と同じ表）。判定できなかったときも止める（503）。
layout.tsx の判定は残してある（二重防御）。

確認（dev）: 非運営で `/admin`・`/admin/plans`・`/admin/approach-range`・`/admin/candidates`・`/admin/companies` が 403・データ0件 ／
server action の POST も 403 ／ 運営は 200 ／ 未ログインは 307。

## ほかに同じ形が無いか

**layout だけで守っているページは、同じ形で漏れる。** `/biz` は各ページが `getTenantContext()` を自分で呼ぶので該当しない想定だが、
確かめるなら「権限の無いアカウントで開いて、HTML にデータが入っていないか」を数える。

## 追記：同じ穴が他に無いかの点検（2026-10-10）

**結論: ページ・API で他社・他人のデータが HTML（RSC を含む）に出る箇所は、ほかに見つからなかった。**
server action で判定の無いものが1件、無効の担当者を通すものが3件あったので直した。

### 調べ方（dev / 本番と同じ DB）

検証用の企業 TYU（担当 contact+21）と求職者 contact+04 のあいだに、**目印の文字列**を入れた行を作った
（会話とメッセージ・面談申込・声かけ・提案）。あわせてセールスフォースの**非公開求人の題名**（求職者側には出ない）も目印にした。
次のアカウントで各ページを開き、HTML に目印が入るかを数えた。

| アカウント | 立場 |
|---|---|
| contact+36（ZAP の担当） | **別の企業の担当者** |
| contact+36 ＋ cookie `biz_current_company_id` を TYU に書き換え | **所属していない企業への切り替えを偽装** |
| contact+15 | 企業に所属していない求職者 |
| 未ログイン | — |
| ★contact+21（TYU の担当）／ contact+08（セールスフォースの担当）／ contact+04（本人） | **陽性対照**（入っているべき人） |

対象: `/biz` の17ページ ＋ 他社の id を入れた動的ページ4つ（会話・求人の編集・求人のプレビュー）、
`/mypage` の11ページ（他人の会話の id を含む）。`/admin` の26ページ、`/api/admin` の9ルート（全メソッド）。

### 結果

- 権限の無い4つの立場で、目印は **0件**（他社の会話・面談申込・声かけ・提案・非公開求人のいずれも）。
  - 1件だけ出た「セールスフォースの企業 id」は、公開のロゴ画像の URL（おすすめ企業の欄）で、非公開の情報ではなかった。
- 陽性対照: 本人・その企業の担当者では、目印がすべて入っていた（会話・面談申込・声かけ・提案・非公開求人）。
- cookie の偽装: 所属していない企業には切り替わらない（`getCompanyContext` が所属を確かめている）。
- `/admin` 26ページ: 非運営は 403・目印0件、運営は 200（陽性対照: 運営の `/admin/jobs/[id]` に非公開求人の題名が入る）。
- `/api/admin` 9ルート: 非運営・求職者はすべて 401 か 403。

### 直したもの

| どこ | 何が問題だったか |
|---|---|
| `src/app/admin/placements/actions.ts` | **運営かどうかを1つも確かめていなかった**（admin クライアントで作成・更新・削除）。守っていたのは layout と middleware だけ。各操作の頭で `auth_is_admin()` を見るようにした |
| `src/app/biz/posts/_actions/{deleteStory,togglePublish,updateStory}.ts` | 所属の確認が `is_active` を見ておらず、**無効にした担当者**でも自社のストーリーを書き換えられた。`is_active = true` を足した |

### layout だけで守っている箇所（2026-10-10 時点）

- `/admin` … layout ＋ middleware（今回）。
- `/biz` … layout は未ログインと所属なしを redirect するだけで、**各ページが `getTenantContext()` を自分で呼ぶ**。
  ページ側が所属で絞っているので、layout に頼っているページは見つからなかった。
- `/mypage` … layout での判定は無い。各ページが本人で絞る。会話の詳細は middleware が参加者でなければ 404。
