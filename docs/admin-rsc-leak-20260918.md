# `/admin` の RSC ペイロード漏れ — 調査と対処

**発見・対処: 2026-09-18**（`/admin/proposals` の通し確認中に見つけた）

---

## 0. 一行で

**`/admin` 配下の6ページが、ログインしていれば運営権限の無い利用者に、
実ユーザーの氏名と非掲載企業の社名を HTML で配っていた。**
**アクセスされた形跡は無い**（ログを全期間さかのぼって確認）。6ページとも塞いだ。

---

## 1. 機構 — なぜレイアウトのガードで止まらないか

`src/app/admin/layout.tsx` は `auth_is_admin()` が false のとき `children` を捨てて
「このアカウントには管理画面の権限がありません」を返す。**画面は正しい。**

しかし **App Router はレイアウトとページを並行して描画する。**
レイアウトが `children` を捨てても、**ページ本体は実行され、その props は
RSC のフライトデータとして HTML の `<script>` に載る。**

```
…\"name\":\"山田 空次郎\",\"isTest\":true},{\"id\":\"b51fc35e-…\",\"name\":\"木村雅樹\",\"isTest\":false},…
```

⚠️★**「画面に出していない」は根拠にならない。サーバーから送らないことだけが担保。**
（⑨で候補者を匿名にするときに `ow_users` を select しない形にしたのと同じ考え方）

⚠️★**status では判定できない。** `admin/layout.tsx` は**意図的に** redirect せず 200 を返す
（`redirect("/")` に戻すと `OnboardingGuard` に捕まって転職の意向を聞かれる画面に飛ぶ。
2026-09-09 の `0f3654cc`。layout.tsx に経緯がある）。**中身で判定すること。**

## 3. ★アクセスされた形跡 — **無し**（修正より先に確認した）

### 3-1. 使えた/使えなかったログ

| 情報源 | 使えたか |
|---|---|
| **Supabase `edge_logs`** | ★**使えた。** 2026-09-09 まで遡れ、`request.sb.auth_user`（呼び出した本人の auth id）を持つ |
| Vercel のランタイムログ | ❌ **9日前まで届かない。** CLI は**件数**で切るため、5,000件でも**12分ぶん**しか取れない（`--limit 5000` で 2026-09-18 11:21〜11:32）。全期間を見るには Log Drain が要る |
| `ow_page_views` | ❌ 使えない。**67行・全部 2026-07-13**・`/admin` は0件（実質死んでいる） |

### 3-2. 何を数えたか

`/admin/*` はレイアウトが**必ず** `auth_is_admin()` を RPC で呼ぶ。
したがって **「サーバーから呼ばれた `auth_is_admin` で、呼び出し本人が運営でないもの」
＝ 運営でない人が `/admin` に到達した回数**。

⚠️ `auth_is_admin` は `CompanyAdminDndOverlay`（企業ページ）からも**ブラウザ**で呼ばれる。
   こちらは運営でない人が呼んで**当たり前**なので、混ぜてはいけない。
   → `request.headers.x_client_info` で分けた:
     `createServerClient`（ua=node）= **ページの描画** ／ `createBrowserClient` = オーバーレイ

```sql
select toDate(timestamp) day, log_attributes['request.sb.auth_user'] auth_user, count(*) n
  from logs
 where source='edge_logs'
   and log_attributes['request.path']='/rest/v1/rpc/auth_is_admin'
   and position(log_attributes['request.headers.x_client_info'],'createServerClient')>0
   and log_attributes['request.sb.auth_user'] not in ('<admin1>','<admin2>')
 group by day, auth_user
```

### 3-3. 結果

**2026-09-09 00:00 〜 2026-09-18 12:00 UTC を24時間ずつ10窓に分けて全期間を走査した。**

| 日 | 運営でない人のサーバー側 `auth_is_admin` |
|---|---|
| 09-09 / 09-10 / 09-11 / 09-12 | **0** |
| 09-13 / 09-14 / 09-15 / 09-16 | **0** |
| 09-17 | **0** |
| **09-18** | **17回** — ただし全て **`contact+01` と `contact+07`（`is_test`）で 11:18〜11:20 UTC**、
★**この調査のために私が行った検証そのもの** |

→ ★**実在の利用者による到達は 0件。**

⚠️★**検出器が効くことは確認済み。** 上の 09-18 の17回が**陽性対照**になっている
（私の検証が検出できている＝クエリは実際に到達を拾える）。
**「0件でした」を、検出器が壊れている0と取り違えていない。**

⚠️ 前提: 未ログインの訪問者は middleware が 307 で弾くのでレイアウトに到達せず、
   そもそも HTML が作られない。**漏れうるのはログイン済みの非運営だけ**で、
   それがこの数え方の対象。

## 4. 対処 — ページ本体でも確かめる

判定は [lib/auth/adminPageGuard.ts](../src/lib/auth/adminPageGuard.ts) の `viewerIsAdmin()` に集約。

```ts
export default async function Page() {
  if (!(await viewerIsAdmin())) return null;  // 画面はレイアウトが出す
  const db = createAdminClient();             // ★ここから下で初めて DB を触る
```

| 決めごと | 理由 |
|---|---|
| **レイアウトのガードは残す（二重）** | ページ側は「データを取らない」ため、レイアウトは「画面を出さない」ため。役割が違う |
| **DB を引く前に返す** | 引いてから捨てても、取得そのものは起きる |
| **`notFound()` にしない** | レイアウトが出す「別のアカウントで入り直す」導線を消してしまう |
| ★**`isAdmin()`（lib/auth/isAdmin.ts）を使わない** | あちらは `ADMIN_EMAILS` も見るが、**レイアウトは `auth_is_admin()` だけ**。述語がずれると、`ADMIN_EMAILS` にだけ載っている人で**同じ漏れが復活する** |

⚠️★**レイアウトと同じ述語であることが、この関数の唯一の要件。**
   `admin/layout.tsx` の判定を変えるときは必ずここも一緒に変える。

**同じ方法**（運営権限の無い `is_test` セッションで HTML を取得し、実ユーザーの氏名と

|---|---|---|---|---|
| `/admin` | 1 | 5 | **0** | **0** |
| `/admin/placements` | **9** | **40** | **0** | **0** |
| `/admin/companies` | 2 | **40** | **0** | **0** |
| `/admin/candidates` | **9** | 0 | **0** | **0** |
| `/admin/ambassador-requests` | 5 | 0 | **0** | **0** |
| `/admin/proposals` | 8 | 0 | **0** | **0** |
| `/admin/jobs`（元から漏れていない） | 0 | 0 | 0 | 0 |

### ★2つの対照で確かめた（0件を信じる前に）

| 対照 | やったこと | 結果 |
|---|---|---|
| ① **検出器が効くか** | `/admin/candidates` の guard を1つ外す | **氏名9件を再検出**（＝0件は本物） |
| ② **運営の画面を壊していないか** | `viewerIsAdmin()` を `true` 固定にする | **修正前の数字が正確に再現**（1/5・9/40・2/40・9・5）。＝ 運営には従来どおり出る |

⚠️★②が重要。ガードを足すと**運営自身が見られなくなる**危険があるが、
   述語がレイアウトと同一なので「レイアウトを通れる人はページも通る」。
   数字の一致がそれを裏づけている。

## 6. 同じ形が他に無いか（調査のみ・今回は直さない）

**レイアウトで認可を判定しているのは `admin/layout.tsx` だけ。**
他のレイアウトは redirect しており、**本文の無い 307** になるので漏れない。

`/biz` を実測（企業に属さない求職者 `contact+01` のセッション）:

| | |
|---|---|
| `/biz` `/biz/dashboard` `/biz/candidates` `/biz/members` `/biz/employees` `/biz/company` `/biz/jobs` `/biz/meetings` `/biz/proposals` `/biz/scouts` | **全て 307 ／ 氏名0 ／ 非掲載社名0** |

`/biz/layout.tsx` は `redirect("/biz/auth")` を使っている。
自前の認可を持たない `page.tsx` は27件中3件だが、いずれも**公開ページ**
（`/biz`・`/biz/auth`・`/biz/auth/accept-invite`）で、レイアウトの除外パスに入っている。

→ ★**`/biz` に同じ形は無い。**

⚠️ ただし**API ルートと Server Action は別の話**。あちらは自分で認可を見ている
（CLAUDE.md「認可の有無を、共通関数名の出現回数で判定しない」）。今回は対象外。

## 7. 次に触る人へ

⚠️★**`/admin` にページを足すときは、`viewerIsAdmin()` をページ先頭に置くこと。**
   レイアウトのガードは画面を守るだけで、**データは守らない。**

⚠️★**確かめ方は「HTMLを非運営セッションで取得して grep」。** 画面を見ても分からない。
   status も 200 のままなので当てにならない。

⚠️ 0件を信じる前に、**guard を1つ外して検出できることを確かめる**こと（5章の対照①）。
