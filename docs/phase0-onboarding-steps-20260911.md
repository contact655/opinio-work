## ★3画面に割るときの選択肢

### (a) 各ステップで保存する

| | |
|---|---|
| 良い | **1画面目で離脱しても職歴が残る。** いまの3人の損失が消える |
| ⚠️ 悪い | **`onboarding_completed` をいつ立てるかが割れる。** 1画面目で立てると `OnboardingGuard` が2・3画面目へ誘導しなくなり、**stance 未回答のまま抜ける人が増える**（＝候補者検索に出ない人が増える） |
| ⚠️ 悪い | 職歴の POST が**作成**なので、戻って直すと **2件目ができる**。更新に切り替えるか、戻れなくする必要がある |

### (b) 最後にまとめて保存する（現行と同じ）

| | |
|---|---|
| 良い | いまと同じ。**戻って直しても1件**。実装が増えない |
| ⚠️ 悪い | **3画面に伸びたぶん、離脱で失う量が増える。**（いま2画面で3人。3画面ならもっと） |

### (c) 1画面目だけ保存し、2・3は都度

| | |
|---|---|
| 良い | **保存に必要な3点は確実に残る。** 2画面目以降は「足すだけ」なので作成でも二重にならない |
| ⚠️ 悪い | 1画面目に戻って会社を直したときに**更新が要る**（作成した id を state に持つ） |
| ⚠️ 悪い | `onboarding_completed` の扱いは (a) と同じ問題が残る |

## ★私の推奨 ── **(c)。ただし `onboarding_completed` は最後に立てる**

理由は3つ。

1. **失って困るのは1画面目だけ。** 2・3画面目は任意項目と意思表示で、あとから
   `/mypage` で入れられる。⚠️ **職歴だけは入口で取れないと、そのあと誰も入れない**
   （実データ: 実ユーザー11人中、職歴があるのは4人）。
2. **`onboarding_completed` を最後に立てれば、いまの `OnboardingGuard` の挙動が変わらない。**
   途中離脱者は次回ログインでまた `/onboarding` に来る。⚠️ そのとき
   **1画面目は「もう保存済み」なので、作成ではなく更新になる**（下記の宿題）。
3. (a) と違い、**戻って直す経路が1画面目の1件だけ**に閉じる。

⚠️★**(c) を採るなら、先に決めることが1つある。** 2回目に来た人の1画面目をどうするか。

| 案 | |
|---|---|
| c-1 | **既存の職歴を読み込んで更新する**（id を持つ）。⚠️ 実装が増える |
| c-2 | **1画面目を飛ばす**（既に職歴があるなら2画面目から）。⚠️ 直したい人が直せない |

## 画面間で state をどう持つか

| 案 | |
|---|---|
| ★**親コンポーネントの state ＋ URL の `?step=`** | **推奨。** 戻る/進むがブラウザの戻るで効く。リロードで消えるのは (c) なら1画面目が保存済みなので損が小さい |
| URL だけ（値も URL に） | ⚠️ 会社名などが URL に出る。**やらない** |
| `sessionStorage` | ⚠️★**`OnboardingGuard` で一度踏んでいる。** 「`true` だけ覚える／`false` を覚えると無限ループ」「条件を足したらキーに `.v2` を付ける」。**同じ罠を踏まないこと。** 値を覚えるなら**キーにバージョンを付け、完了時に必ず消す** |

⚠️ `?step=` は `searchParams` を読むので、**`useSearchParams()` の Suspense 境界**が要る
（`OnboardingPage` は既に `Suspense` で包んである。そこに乗せる）。

## `scoreJob.ts` の扱い ── ★**件数でスコアは散らない**

```ts
const hit = job.roleIds.some((id) => wantIds.includes(id));
if (hit) score += WEIGHTS.JOB_TYPE;
```

**当たれば1回だけ加点**（`some`）。**何件持っていても加点は同じ。**
⚠️ したがって「多いほど散る」ことは無い。**上限3つの根拠はスコアではない。**

⇒ 上限を3にする理由は**画面の都合**（選びすぎると何を求めているか読めない）。
⚠️ ただし**理由が1つ弱くなる**ので、3にするか5のままにするかは判断が要る。
   ⚠️ `IntentCard` は **5**。**揃えないと同じ設定に2つの上限**ができる。

# 実装後に残した穴（2026-09-11 / 2画面化の時点）

**会社は入れたが職種か入社年月が欠けている人には、勤務地・勤務形態が出るが保存されない。**

`prefecture` / `remote_work_status` は現職の職歴の行に載る値で、送るのは
`saveCurrentExperience()` だけ。その関数は `canSaveExperience`（会社・職種・入社年月の3点）で
早期に return するので、3点が揃っていないと入力しても行ごと作られない。

⚠️ **いまは直さない。** 「次へ」で出る警告（「…が未入力です。このまま進むと、
   直近のお勤め先は職歴として保存されません。」）がこの場合を指しているため。

⚠️★**画面が3つになったら再確認すること。** 警告は1画面目の CTA に出るが、
   勤務地・勤務形態は別の画面にある。**警告を読んだ画面と、捨てられる入力欄の画面が
   離れる**ので、いまの「警告でカバーされている」が成り立たなくなる可能性がある。

⚠️ 会社そのものを入れていない人には、勤務地・勤務形態・「この会社に役割を追加」は
   **出ない**（`hasCompany` で囲ってある。2026-09-11 実測）。**外さないこと** ——
   保存先が無い欄を出すのは「入力させたのに保存しない」になる。
