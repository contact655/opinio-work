## 設計判断の確定（4ポイント）

### 1. 同社グループ化ロジックの実装場所 → MergedTimeline 内部で拡張

career.ts には触らない（未使用関数 `groupOverlappingCareers` / `calculateTenure` の存在から
整理タスクは別プロジェクト相当と判断、今日のスコープから明確に除外）。

理由：
- MergedTimeline には既に `buildParallelMap` / `groupParallelEntries` という同レイヤーの
  グループ化機構がある。RenderEntry に `"career-group"` バリアントもあり、同社グループ化は
  「直交する追加機能」として自然に挟める
- 既存ロジックを参考にすると `groupParallelEntries` と同じパターン（連続走査）でも実装可能

### 2. 型の不一致問題（snake_case vs camelCase） → MergedTimeline の snake_case に統一

career.ts は camelCase だが、誰も使っていない（呼び出し元ゼロ）。実際に動いている3画面は
すべて snake_case で統一済み。「動いている方の規約」を正とする方が、未使用コードを基準に
するより合理的。

### 3. グループ化のキー規約 → CareerHistoryEditor の `groupStints()` と同じ

- master 企業（company_id あり）: `m:${company_id}`
- custom 企業（company_text）: `c:${company_name}`
- anon 企業（company_anonymized）: `a:${id}`（個別扱い、誤統合防止）

### 4. 出戻りパターンの扱い → 連続走査で別グループに分かれる（Y案 = C案）

柴さんの回答「会社2回登録ですね！」から確定：
- DB には A社の経歴が2行存在
- UI でも別グループとして表示（連続走査ロジックなら自然にそうなる）
- 入力時に2行登録した意図（出戻りを明示したい）と表示が一致

これが後の `/profile/edit` バグ発見の伏線になった（後述）。

## 出戻りバグの発見と原因特定（コード分析だけで確定）

### 発見の経緯

`/profile/edit` で出戻りパターンのテストデータ（003 → 001 → 003）を入力したところ、
**003 が3件全部1グループに統合され、在籍期間が「2018.04 〜 現在 · 8年2ヶ月」と表示される
誤表示**を発見。期待は「PMM を挟んで上下に分かれる」だった。

### 原因調査のアプローチ

Claude Code に「**コードを実機で動かす前に、まずコードレベルで両関数を比較してくれ**」という
依頼の仕方が当たった。グレーゾーンの早合点を避け、コード分析だけで確実な切り分けに到達できた。

### 確定した原因

| 画面 | 関数 | 方式 | 出戻り |
|---|---|---|---|
| `/profile/edit` | `groupStints()` | **Map 全件集約**（位置無視） | ❌ バグあり |
| `/u/[id]` / `/mypage` | `groupSameCompanyEntries()` | **連続走査**（位置依存） | ✅ 正しい |

`groupStints` の実装（CareerHistoryEditor.tsx 行62〜68）:
```typescript
const map = new Map<string, Stint[]>();
for (const s of stints) {
  const k = groupKey(s);
  if (!map.has(k)) map.set(k, []);
  map.get(k)!.push(s);    // ← 位置に関係なく全件を同じキーに集約
}
```

これは Map による全件一括集約。`m:003` キーの Stint は出戻りの 001 を挟んでいても
全部同じグループに入る。

`groupSameCompanyEntries` の実装（今日追加）は連続走査:
```typescript
while (next.kind === "career" && getCompanyKey(next.data) === key) {
  group.push(next.data);
  j++;
}
// break on first different company → 出戻りは自然に別グループ
```

001/PMM で break するため、003 は ① (FS+IS) と ② (FS) に分断される。

### 実機検証

`/u/[id]` と `/mypage` で実機目視確認したところ、コード分析の結論通り出戻りパターンが
正しく3グループに分断表示されることを確認:

- 上の 003 グループ: FS(2024.04-現在) + IS(2022.04-2024.03)、在籍期間 4年1ヶ月
- 真ん中: 001 / PMM(2020.04-2022.03) 単独カード
- 下の 003: FS(2018.04-2020.03) 単独カード

**今日のリリース（commit eb712f6）は無傷で、完全に成功**。バグの本体は昨日実装した

## 今日の学び（恒久ルール候補）

### コード分析だけでも原因特定はできる

出戻りバグの調査で、Claude Code が `groupStints` のコードを読んで Map 全件集約だと
特定した時点で、実機を動かす前にバグの所在を確定できた。「実機で確認」を絶対視せず、
**ロジックレベルで切り分けが付く問題はコード分析で済ませる** のは時間効率が高い。

ただし、Visualizer や Vercel キャッシュなど不確定要素が絡む場合は実機確認が必須。
切り分けに使う判断軸: 「症状の原因がコードの中だけで完結するか、外部環境に依存するか」。

### 調査指示書は「精度を上げながら段階的に絞る」のが正解

v2 → v3 → v4 で範囲を絞り込みながら確実性を上げていったアプローチが機能した。
「全部一度に取りに行く」より、「次の判断に必要なものだけを取りに行く」を3回繰り返した。
v3 で「3画面の型が完全に snake_case で揃っている」が確定したことで v4 の問いが
「company_id を握っているか」だけに絞れた。

### 「未使用関数は触らない」の原則

career.ts の `groupOverlappingCareers` / `calculateTenure` は呼び出し元ゼロのデッドコード
だった。これを「整理しようとして共通化に使う」発想に走らなかったのが今日の正解。
別ファイルに切り出すと「共通化したつもりで複雑性が増える」典型パターンに陥っていた。
未使用関数の処遇は今回のスコープ外として明確に切り出し、専用タスクに分離した。

### 連続走査 vs Map 全件集約の設計選択

同じ「同社をグループ化する」要件でも、実装方式によって出戻りパターンの可否が決まる:
- **Map 全件集約**: 実装はシンプルだが、位置情報が消える → 出戻り不可
- **連続走査**: ソート済み配列の隣接エントリのみグループ化 → 出戻り自然対応

今後同類の「順序を保ちながら何かをまとめる」要件が出たら、まず連続走査を検討する。

### 「セッション終盤の新発見は明日に回す」を守る

セッション7〜8時間目に発見した出戻りバグについて、`groupStints` の修正は今日中にやらず
明日に回す判断ができた。昨日の反省を恒久ルールとして守れた。判断疲労の中で
CareerHistoryEditor の UI 周辺との整合を確認する作業は、明らかに品質リスクが高かった。
