# 企業側の画面で `visibility_company` を効かせた（2026-09-10）

`createAdminClient`（RLS バイパス）で `ow_experiences` を引く企業側の画面が
`visibility_company` を見ておらず、**本人が「会社名は伏せる」を選んでも実名が出ていた。**

**同じ問題を計3箇所で踏んでいる。** 2026-08-13 の `/biz/employees` が1箇所目。

| いつ | どこ | 症状 | 対応 |
|---|---|---|---|
| 2026-08-13 | `/biz/employees` | 伏せた人が**その勤務先の採用担当者には実名で見えていた** | `.eq("visibility_company","real")` |
| **2026-09-10** | **`/biz/candidates`** | 同じ。⚠️ **絞り込み・フリーワードでも当たっていた** | 社名を **「非公開企業」に置換** |
| **2026-09-10** | **`/api/biz/company/members`** | 伏せた人の**氏名**がオフィス写真のタグ付け候補に並んでいた | `.eq("visibility_company","real")` |

## 判断の根拠 ── 1箇所目のコメントがそのまま効いた

`/biz/employees/page.tsx:43-60` にこう書かれている:

> 伏せた人が気にしているのは「社名が出ること」ではなく
> **「転職を考えていると今の会社に知られること」**なので、
> ここに出るのはチェックボックスの文面から誰も予想できない。
>
> 企業側が失うものは無い。`masked` / `hidden` の人は公開側にも出ていないので、
> 社員管理画面（＝公開時の見え方を調整する画面）で企業がすることが元から無い。

## 2箇所で扱いが違う理由

| | 扱い | なぜ |
|---|---|---|
| `/biz/candidates` | **社名を「非公開企業」に置換**（行は残す） | 候補者検索は**人を探す**画面。`career_stance` に答えて「声をかけられてもよい」と意思表示した人を、**社名の設定を理由に検索から外すのは本人の選択と矛盾する**。伏せると言ったのは社名であって本人ではない |
| `/api/biz/company/members` | **行ごと出さない** | ここは**人を並べる**画面（オフィス写真のタグ付け）。社名の欄が無いので置換する先が無い。`/biz/employees` と同じ |

⚠️★**`/biz/candidates` で空欄にしないこと。** 企業側から「離職中」または「未入力」に見え、
**社名が出るのとは別の不利益**を本人に与える。
実際、画面には**会社名が空の候補者が既に存在する**（職歴0件の人。下記「柴 久人の件」）ので、
空欄にすると**その状態と区別がつかなくなる。**

## 文言 ── 既存の語彙に揃えた。`masked` と `hidden` で分けない

**`MASKED_COMPANY_LABEL`（`lib/experiences/companyName.ts`）＝ 「非公開企業」。**
`generateMaskedCompanyLabel()`（`lib/utils/timeline.ts`）のフォールバック・
`/mypage/details`・`MergedTimeline` の判定と**同じ文字列**。**新しく作っていない。**

### 分けなかった理由

| # | |
|---|---|
| ① | 候補者検索は**「どの会社の人か」で絞る画面**。代替ラベル（「SaaS（シリーズB・50名規模）」）は**絞り込みに使えない** |
| ② | `hidden` は `masked` より**強い意思**なので、弱い表示にはできない |
| ③ | 置いても**企業側に新しい状態が1つ増えるだけ** |

### 既存の各面での扱い（実装から。揃えるために先に調べた）

| 面 | `masked` | `hidden` |
|---|---|---|
| `/u/[id]` のタイムライン | ラベル置換（`generateMaskedCompanyLabel()`）／どれも無ければ「非公開企業」 | **行ごと出さない**（`timeline.ts:159`） |
| `/companies/[id]` の現役社員 | 出る（社名はその企業ページ自身なので伏せる意味がない） | **出さない**（`queries.ts:1780`） |
| `/biz/employees` | **出さない** | **出さない** |
| `/search` の人物カード | — | 行ごと出さない |

## ★ 絞り込みも同時に塞がる

`/biz/candidates` の**会社名フィルタ**（`CandidatesClient.tsx:291`）と
**フリーワード**（`:268`）は、**どちらも同じ `c.currentCompany` を読む。**
`currentCompany` はサーバー（`page.tsx`）で `resolveExperienceCompanyName()` から作るので、
**そこで置き換えれば表示と検索の両方が塞がる。**

⚠️★**「表示は伏せたが検索では当たる」は、伏せていないのと同じ。**
   フィルタに社名の生値を渡す経路を新設しないこと。

## 実測（dev / c 案 ＝ `is_test` の除外を一時的に外して測った）

### ★なぜ `is_test` の除外を外したか

`/biz/candidates` は **`is_test = false` を要求する**（`page.tsx:232`）。
つまり**検証用アカウントは原理的にこの画面に出ない。**

- **a案（実ユーザーの `visibility_company` を一時的に切り替える）は採らなかった。**
  本人が設定した値を本人の知らないところで変えることになる（`auth_id` NULL の件で
  「本人の設定を運営が代われない」と決めたのと同じ線）
- **b案（実測せずコミット）も採らなかった。** 2箇所とも過去に同じ事故を踏んでいる箇所
- ⇒ **c案**: dev で `.eq("is_test", false)` を一時的に外し、測定後に戻した。
  ⚠️ **戻し漏れが無いことを SHA-256 の一致で確認**（`d36bd1117ea8c50b`）。
  ⚠️ 外しているあいだ push していない。

検証のため送信元企業（セールスフォース）を一時的に `paid` にした（候補者検索が有料機能のため）。
**測定後に `free` へ戻している。**

## 別件: 柴 久人の行が `/biz/candidates` で会社名が空欄だった理由

**原因は「現職の職歴が存在しない」。** ⚠️ **データは直していない。**

同名のアカウントが**3つ**ある（一覧に2つ出ていたのはこのため）。

| email | 氏名 | `is_test` | 職歴（全体 / 現職） | `career_stance` |
|---|---|---|---|---|
| `hshiba@opinio.co.jp` | 柴久人 | **true** | **0 / 0** | `active` |
| `s.hisato1020@gmail.com` | 柴 久人 | **false** | **0 / 0** | `open` |
| `hshiba+01@third-box.jp` | 柴 久人 | **true** | **0 / 0** | NULL |

⇒ **3つとも `ow_experiences` が0件。** `company_id` / `company_text` が空なのではなく、
**行そのものが無い。** 別の条件で落ちているわけでもない。

⚠️★**これは「会社名が空の候補者が既に存在する」ことの実例。** 伏せた人を空欄にすると
   この状態と区別がつかなくなるので、「非公開企業」と明示する判断の裏付けになっている。

⚠️ `is_test = false` の `s.hisato1020@gmail.com` が**実ユーザーとして候補者検索に出ている**。
   意図した状態かは未確認（本調査の範囲外）。
