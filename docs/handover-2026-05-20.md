## Migration 106：3回試行の記録

### 試行1・試行2：FK制約エラーで失敗

1回目の migration では ow_experiences_role_category_id_fkey の DROP を忘れており、
`ERROR: update or delete on table "ow_roles" violates foreign key constraint` で失敗。

2回目で ow_experiences と ow_roles 自己参照の FK を追加したが、今度は
ow_jobs_role_category_id_fkey が存在することが発覚してまた失敗。

**教訓**：ow_roles を参照する FK 制約を調べるには、テーブル名を人間が推測するのでなく：
```sql
SELECT conname, conrelid::regclass
FROM pg_constraint
WHERE confrelid = 'ow_roles'::regclass AND contype = 'f';
```
で全件取得すべきだった。ow_jobs に FK があるのは想定外だった。

### 試行3：成功（commit b7a0f3c）

全4つの FK 制約を DROP/ADD で囲んだ最終版：
- ow_roles_parent_id_fkey（自己参照）
- ow_experiences_role_category_id_fkey
- ow_jobs_role_category_id_fkey
- ow_company_employee_categories_role_id_fkey

migration 自体は BEGIN...COMMIT トランザクションで保護されており、
失敗した試行1・試行2は PostgreSQL が完全ロールバックしていたため
DB は常に29行のままだった。トランザクション保護が正しく機能した事例。

### migration 106 の内容（案Y改：旧→新マッピング方式）

前セッションで仕様書の「案Y（全部その他に寄せる）」から変更した経緯もあり確認。
新方針は「可能な限り旧→新マッピング、対応するものがない場合のみその他に集約」。

主なマッピング：
- CEO/COO/CFO/CTO/CPO（旧5行） → 経営・CxO（新1行）
- PdM/PM + プロダクトオーナー → プロダクトマネージャー
- HRBP + エンタープライズ営業 + SDR/BDR → その他（対応する新項目なし）
- SRE/インフラ、iOS/Android → 表記揺れのみ吸収（実質同一）

ow_company_employee_categories は UNIQUE 制約（company_id, role_id）のため、
同一企業の複数行が同じ新 role_id にマップされる場合は DISTINCT ON で重複排除。

## Phase 2-A：求職者UI の動的化

「slug 経由の3層変換」を「UUID 直接処理」に簡略化する作業。3サブフェーズで完了。

### なぜ slug があったのか（背景）

もともと CareerHistoryEditor.tsx には ROLE_OPTIONS（slug + label のペア配列）が
ハードコードされていた。DB には UUID で保存されているが、コードは slug で扱い、
保存時に slug → DB名 → UUID の2段階変換を行っていた。

この設計の問題は「ow_roles マスタを変更するたびに、フロント・API の slug 変換
テーブルも手で書き換える必要がある」点。今回の21項目再設計でその欠点が露わになった。

page.tsx（Server Component）で ow_roles を取得し、ProfileEditClient 経由で
CareerHistoryEditor まで流下させる props バケツリレーを確立。

この時点では CareerHistoryEditor はまだ ROLE_OPTIONS を使っており、
roles prop は `_roles` として受け取るだけ（ESLint の no-unused-vars 対応）。
expand フェーズとして、旧機構（ROLE_OPTIONS）と新機構（roles prop）が

## アーキテクチャ変更の記録

slug 経由の3層変換が UUID 直接処理に簡略化された：

```
【旧】
DB(UUID)
  → GET: DB_NAME_TO_SLUG → slug → クライアント表示
  → POST/PUT: slug → SLUG_TO_DB_NAME → DB名 → ow_roles検索 → UUID保存

【新】
DB(UUID)
  → SSR: UUID → roleNameById.get(uuid) → 日本語名をラベルとして利用
  → POST/PUT: UUID → UUID_RE.test() で検証 → そのまま保存
```

これにより /profile/edit はマスタ変更に対して耐性のある実装になった。
今後 ow_roles を変更してもフロント側のコード変更が不要。
（/biz/organization で先行していた「DB動的取得方式」を /profile/edit にも適用した形）

## 今日の学び（恒久ルール候補）

### FK制約の調査方法

migration で特定テーブルを参照する FK 制約を調べる際は、テーブル名を人間が
推測して列挙するのではなく、以下 SQL で全件取得してから着手すること：

```sql
SELECT conname, conrelid::regclass
FROM pg_constraint
WHERE confrelid = 'テーブル名'::regclass AND contype = 'f';
```

今回の ow_roles は4つ FK があり、ow_jobs の存在が想定外だった。

### expand-contract での段階実装

Phase 2-A-1（パイプライン追加・旧機構は温存）→ 2-A-2（旧機構削除・新機構有効化）→
2-A-3（旧 API 層クリーンアップ）という3段階の手順で、各サブフェーズ完了時点で
本番が壊れない構造を維持できた。旧コードと新コードを一時的に共存させ、
削除は確認後にまとめて行う expand-contract パターンの実践例として残す。

### push 確認の徹底

前セッション末に「push 完了」と報告したが実際には push していなかった（commit のみ）。
Vercel のデプロイ一覧に表示されないことを柴さんが確認して発覚。

以降は push 後に必ず `git log origin/main --oneline -3` で実測確認し、
ローカル hash とリモート hash の一致を数字で報告する。

### 動的取得方式 vs ハードコード方式

ハードコードは「実装が速い・ファイルが閉じている」が、マスタ変更のたびに
複数ファイルの定数テーブルを手で書き換える必要がある（今回の slug 変換系が典型）。
DB 動的取得は初期コストはやや高いが、マスタ変更耐性が段違いに高い。
IT/SaaS 業界特化のマスタは今後も微修正が発生する前提で設計し、
動的取得方式を標準とする。

## Phase 3 完了（commit 9a02ccd）

親子排他制御を実装。変更規模：+35行 / -16行。

### 実装内容

**① `toggle()` 拡張**

```typescript
function toggle(id: string) {
  const role = allRoles.find((r) => r.id === id);
  setSelected((prev) => {
    const next = new Set(prev);
    if (next.has(id)) {
      next.delete(id);
    } else {
      next.add(id);
      if (role?.parentId === null) {
        // 親を選択 → 子を全除去
        const children = childrenByParent.get(id) ?? [];
        for (const child of children) next.delete(child.id);
      } else if (role?.parentId) {
        // 子を選択 → 親を除去
        next.delete(role.parentId);
      }
    }
    return next;
  });
}
```

**② 親チェックボックス disabled 条件追加**

```typescript
const isParentDisabledByChildren = children.length > 0 && children.some(
  (child) => selected.has(child.id) || currentRoleIds.has(child.id)
);
const isParentDisabled = isParentAdded || isParentDisabledByChildren;
```

**③ 子チェックボックス disabled 条件追加**

```typescript
const isChildDisabledByParent = selected.has(child.parentId!) || currentRoleIds.has(child.parentId!);
const isChildDisabled = isChildAdded || isChildDisabledByParent;
```

cursor・color・onChange ガードはすべて新しい `isParentDisabled` / `isChildDisabled` で統一。
新規 CSS なし、既存グレースタイル（`var(--ink-mute)`）を流用。

### 本番動作確認済み

### UX 課題（次セッションで判断）

仕様書6.2 は「親追加と子追加を排他制御」と明記されており、現実装は仕様通り。
ただし「子をやめて親に切り替えたい」ときに一度子のチェックを外す必要があり手間がかかる。

選択肢：

| 案 | 挙動 | 印象 |
|----|------|------|
| a. 現状維持 | disabled（クリック不可） | 厳格・明快 |
| b. 自動排除 | クリック可、相手を自動解除 | 直感的・UX良い |
| c. 警告のみ | 共存を許容して警告表示 | 緩い |

**次セッションで案 b を検討する**（toggle の中での相手解除はすでに実装済みのため、
