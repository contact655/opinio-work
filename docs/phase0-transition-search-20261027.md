## 5. 案

### 5-1. 入力の読み取り：決まりで作る

| | 決まり（正規表現・辞書） | AI で条件に変える |
|---|---|---|
| 準備 | いまの `interpretQuery` に「移動の語」を足すだけ | SDK も環境変数も無い。新しく入れる |
| 約束（マスタに解決できた語だけを条件にする） | そのまま守れる | AI の出力をもう一度マスタに解決する段が要る（`interpretQuery.ts:48-51` の約束） |
| 拾える言い方 | 下の型。言い回しの揺れは辞書を足していく | 揺れに強い |
| 費用・速さ | 0・速い | 呼ぶたびに費用と待ち時間 |
| 推奨 | ★**こちら**。データが10人規模のうちは、AI で読めても出す結果がほぼ同じ | データが増えて言い方が広がってから |

決まりで拾える型（社名 X・業界 G・職種 R はいまの辞書で解決する語）:

| 型 | 例 | 読み取った条件 |
|---|---|---|
| X を出た／辞めた／卒業した／退職した | Salesforceを出た人 | X の職歴があり、X に今いない |
| X 出身／X から来た／X を経て／元 X | Salesforce出身 | 同上（2と1を同じ意味にする） |
| X から転職した | Salesforceから転職した人 | 同上（いま「転職」が読めない件もこれで直る） |
| X に入った人の前職／X の前は | Salesforceに入った人の前職 | X に入る直前の会社（集計を出す） |
| X を出て G／R に行った | Salesforceを出てCSに行った人 | X の直後の会社が G、または直後の職種が R |
| G から来た／G 以外から X（または G2）へ | IT以外から来た人 | 直前の会社の業界が G（以外）で、次が G2 |

⚠️ 「事業会社」「未経験」「大手」は辞書に無い。足すなら意味を先に決める（論点5・6）。
⚠️ 業界の語（「金融」「メーカー」「IT」）を移動の文の中でだけ読む。業界を普通の条件にしない理由（70社が IT）は変わらないため。

### 5-2. チップで見せて直せる形

いまの「条件のチップ」（`search/page.tsx:488-503`）に、移動の条件を1つのチップとして足す。

- 例: 「こう読み取りました： [Salesforce を出た人 ×] [行った先: カスタマーサクセス ×]」
- ×で外すと、移動の条件だけ外れて「Salesforce に在籍したことがある人」に戻る
- 読めなかった語は今どおり「この語では絞り込めません」。★あわせて **1文字の漢字を黙って捨てる規則を見直す**（「出」「来」「入」を移動の語として拾うなら、捨てる前に読む）

### 5-3. 今の AND に混ぜるか、別枠にするか

推奨は **混ぜない。人のタブの「現役／OB・OG」の絞り込みを入口にする。**

- 「出た人」「出身」は、社名の条件で当たった人を「OB・OG」で絞るのと同じ。新しい AND の条件を作らなくても、既にある `?tenure=former` を最初から当てた状態で開けばよい
- 以前「別枠」にしたのは「閲覧者の職歴によって AND の意味が変わる」ため（`phase0-industry-match-20260904.md:438`）。移動の条件は**閲覧者に関係なく同じ意味**なので、その理由には当たらない
- ただし言い方3・4・5は「直前／直後の会社」という新しい種類の条件になる。これは職歴1行への条件（いまの `experienceMatches`）では書けず、**隣り合う2行への条件**になる。いまの「1つの職歴が全部満たす」という AND の約束（`runSearch.ts:642-668`）とは別のものとして、別の関数に分けるのが安全

### 5-5. 「よく移った先」を会社名で出すか、業界でまとめるか

推奨は **業界の大分類でまとめる**（「人の流れ」と同じ）。

- 会社名で出すと、いまのデータでは全部1人ずつで、下限に届くものが0
- 会社名は「誰がどこへ行ったか」を示しやすい。業界の大分類なら3人の下限で出せる
- ⚠️ 検索の「〈会社〉を出た人の、いま」（`destinations.ts`）は会社名で5人の下限、「人の流れ」は業界で3人の下限と、**同じ「出た人の行き先」で2つの規則がある**。どちらに揃えるかは論点3

### 5-6. 「こんな探し方もできます」の例文を0件にしない

- いまの `SEARCH_EXAMPLES`（`examples.ts:9`）は手で選んだ固定の5語
- 移動の例文は、**表示するときに件数を数えて、該当がある文だけ出す**のが安全。候補は「掲載企業で出た人が3人以上いる会社」から作る
- いまのデータでは「Salesforceを出た人」1つだけが条件を満たす。「IT以外から来た人」（8人）は会社を指定しない型

## 6. 柴さんに決めていただきたいこと

1. **言い方1と2を同じ意味にしてよいか。**「Salesforce出身」は「新卒で入った会社」の意味でも使われる。同じ意味（その会社の職歴が全部終わっている人）にすると、実データでは同じ4人になる
2. **入口を「人のタブの OB・OG 絞り込み」にする案でよいか。** 新しいタブや別枠を作らず、移動の語を読んだら OB・OG で絞った状態で開く
3. **「出た人の行き先」の下限と単位をどちらに揃えるか。** 検索の帯（会社名・5人）と「人の流れ」（業界の大分類・3人）が別の規則になっている
4. **言い方3（入った人の前職）を検索で出すか。** 中身は企業ページの「人の流れ」と同じになる。検索では「人の流れ」へ案内するだけにする案もある
5. **「事業会社」をどう読むか。**「IT 以外の業界の会社」「自社でサービスを持つ会社（受託・SIer・コンサルでない）」など。決まらないうちは読まない
6. **「未経験」をどう読むか。** 業界の未経験（IT 以外から IT へ）か、職種の未経験（営業から CS へ）か
7. **会社を指定しない移動（言い方5）で、行き先・前職を会社名で出すか。** 母数が小さいうちは、会社名を出すと個人が分かりやすい。業界の大分類だけにする案
8. **年齢つきの言い方を対象外にしてよいか。** 年齢で絞らせない方針と `age_at_move` を使わない方針に合わせて、読み取らない（「年齢では絞り込めません」と出す）
9. **社名の揺れを `search_aliases` から拾うか。** いまは「セールスフォース」で社名として読まれない。検索の社名照合に `search_aliases` を足すか、セールスフォースに別名を入れるか（後者はデータの変更なので了承が要る）
10. **1文字の漢字を黙って捨てる規則を直すか。**「出た人」「来た人」で、読めなかったことが画面に出ていない

## 付録：使った SQL（要約）

母数はすべて次の条件（`isAggregatableUser` と同じ）で、職歴は `visibility_company = 'real'` だけ。

```sql
with pop as (
  select id from ow_users
  where auth_id is not null and is_test is not true and is_system is not true
    and coalesce(visibility,'') <> 'private' and statistics_opt_out = false
    and lower(coalesce(email,'')) not like '%@seed.internal'
)
```

- ① 全体の数・重なる職歴: 職歴を同じ人どうしで組み、会社の同一性キー（`company_id` → 正規化した社名 → 行ごと）が違い期間が重なる組を数えた → 0
- ② 会社ごと: 会社×人で `bool_or(is_current)`・最初の入社・最後の退職を作り、「出た」「次の会社がある」「前職がある」を数えた
- ③ 移動: `row_number() over (partition by user_id order by started_at, coalesce(ended_at,'9999-12-31'))` で隣り合う2行を組み、同一性キーが違うものを移動とした（`buildMoves` と同じ規則）。業界は `coalesce(親の業種名, 業種名)`、職種は大分類
- ④ 自由入力の社名・セールスフォースの別名: `ow_experiences.company_text` の一覧と `ow_companies` の `brand_name` / `slug` / `search_aliases`
- ⑤ 平均在籍: 出た人の在籍月を `generate_series` で月ごとに並べ、重なりを除いて数えた（`tenureMonths` と同じ数え方）
