## 次セッション最優先 — ログイン不安定の根治（根本原因特定済み）

### 事象
`s.hisato1020@gmail.com` で「ログイン押下 → トップに戻り、未ログイン
表示のまま」が複数回再発。シークレット窓で入力し直すと成功した。
操作ミスではなく **コードバグ**。

### 根本原因（コード読解で確定）
`JobseekerHeader.tsx` に **`onAuthStateChange` の購読が無い**。

```
signInWithPassword 成功（認証は正常）
  → router.push("/companies")  ※クライアントサイドナビ
    → ヘッダーはアンマウントされない（レイアウト継続）
      → useEffect 再実行されない
        → user=null のまま「ログイン」ボタン表示が継続
  → router.refresh() はサーバ再フェッチのみ、client state に無影響
再度「ログイン」クリック → /auth が既存セッション検出 →
router.replace("/") → トップへ → 「何も起きないループ」
```
- ログイン処理（認証）はずっと正常に成功していた。
  「パスワードが違う」「Email/Password認証ではない」は**いずれも誤り**。
  認証は通っており、ヘッダーが state を更新できない構造が真因。

### 別件Aとの関係（事実確定）
- ログイン不安定と別件A（`/mypage` hydration #418/#423/#425）は
  **独立した別バグ**。同根ではない。
  - ログイン不安定: `JobseekerHeader.tsx`（onAuthStateChange無し +
    router.push）
  - 別件A: `MypageClient.tsx`（SSR/CSR ミスマッチ）
- 当初「同根かも」と疑ったが、調査で独立と確定。
  → ログイン不安定は別件Aを待たず**単独で修正可能**。混ぜない。

### 修正方針（実装は次セッション・単独で集中して行う）
`JobseekerHeader.tsx` に2点:
1. `onAuthStateChange` の購読を追加（ログイン状態変化をヘッダーが
   リアルタイム検知。unsubscribe を必ず cleanup で返す。
   二重発火・メモリリークに注意）。
2. `handleLogin` の末尾を `window.location.href` に変更
   （フルリロードで client state を確実に再構築）。

### スコープ規律（厳守）
- `JobseekerHeader.tsx` は全ページ共通コンポーネント。影響範囲最大。
  「ついで」でやらず、**単独セッションで集中**して着手する。
- 実装後: `npm run build` → **`git push origin main` 必須** →
  Vercel が ● Ready をコミットハッシュで確認 → サブページ起点で
  ログイン実機検証（成功後にヘッダーが即ログイン済み表示になるか／
  トップに戻されないか）。
- 別件A・企業マスタ整備と混ぜない。1件ずつ。
- 想定外は即停止・事実で特定してから動く（恒久教訓。今セッションで
  「〜のはず」が4回事実で覆った: admin0件のはず→5/1既存 /
  ow_users.idでいけるはず→FK違反 / 残存セッション原因のはず→
  シークレットでも再現 / 認証失敗のはず→実は認証成功していた）。

- 手動 SQL 実行時、INSERT を2回実行し Salesforce が重複登録された

  検証 SELECT で `c3664ef1...` 1件のみ残存を確認。
- 教訓: 中心テーブルへの手動 INSERT は、
  (a) 直前に存在確認 SELECT を必須化、
  (b) INSERT は WHERE NOT EXISTS 等の冪等化、または name に
      UNIQUE 制約を検討（将来課題として記録）、
  (c) RETURNING で結果を必ず目視確認。
