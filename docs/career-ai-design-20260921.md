## 2. ★スコープ — 2つの別製品を混ぜない

| | ①（これを作る） | 相談相手のAI（作らない） |
|---|---|---|
| 目的 | **本人の希望を構造化する** | 会話そのものが価値 |

## 4. 保存先 — ★`ow_conversations` に同居させない

### 4-1. 同居できるが、しない

構造上は `kind='editor'` に入れられる（§C-2）。**それでも新設する。**

| 理由 | |
|---|---|
| ① | `kind_check` / `kind_consistency` / `stage_consistency` / `role_check` の**4つを同時に広げる**ことになる（＝「UI / API / DB の CHECK を3つ揃える」の対象が4つ） |
| ② | RLS の INSERT が「**発言者が自分の participant**」を要求 → **AIの発言は service_role でしか書けない**。人の会話の前提を最初から曲げる |
| ③ | `body` の CHECK は **1〜8000字**。LLM の応答が入らないことがある |
| ④ | ★**`/mypage/conversations` に人とAIの会話が混ざる。** 企業とのやり取りと同じ一覧に並ぶ |
| ⑤ | ★**⑧が「誰に何が渡るか」を出す画面になる**（§E-5）。同居させると「この会話は相手が居ません」を毎回説明することになる |

### 4-2. 新設する2表

```
ow_career_sessions            1回のインタビュー
  id / user_id(ow_users) / status(active|completed|abandoned)
  started_at / completed_at
  ★model / ★prompt_version        -- どのモデル・どの版で聞いたか（後から再現できるように）
  ★applied_at                     -- 本人が結論を確定させた日時（null = 未確定）

ow_career_messages            発言
  id / session_id / role(user|assistant) / body / created_at
  ★token_input / token_output     -- 費用の実測用
```

⚠️★**`ow_profiles` に会話ログを足さない**（§E-5: 足すと⑧の画面が嘘になる）。
⚠️★**GRANT は配らない。RLS 有効・ポリシー0本・読み書きは admin だけ**
   （`ow_transitions` / `ow_proposals` と同じ形。本人に見せる経路を作る日にポリシーを書く）。
⚠️ `status` は3値で DB の CHECK を張る（UI / API / CHECK の3層）。

## 5. 出力 — ★AIが直接書かない

```
会話 ──▶ AIが「こう理解しました」を出す ──▶ ★本人が確認して押す ──▶ ow_profiles に書く
                                              ▲
                                     ここを飛ばさない
```

| なぜ | |
|---|---|
| ① | ★**本人が言っていないことを保存することになる。** このリポジトリが繰り返し戒めている「値が無いことを、ある値に置き換えない」の、いちばん大きい版 |
| ② | ②の根拠（`preference_match`）は**本人の希望を前提**にしている。推測が混ざると**提案の根拠が推測になる** |
| ③ | 書き戻しに失敗しても**会話は残る**（あとで押せる） |

⚠️★**確定の UI は「AIの文章」ではなく「フォームの初期値」にする。**
   ＝ 会話の結果を**いまある入力欄に入れた状態**で見せて、本人が直して保存する。
   **新しい保存経路を作らない**（既存の `PUT /api/jobseeker/career-preferences` などを通す）。

### 5-1. ★LLM の出力は必ずマスタに解決してから

**`interpretQuery` の約束（§C-3 ④）をそのまま適用する。**

| 引き出すもの | 解決先 |
|---|---|
| 希望職種 | `ow_roles` ＋ `ow_role_aliases`（260行）。★[`desiredRoleOptions`](../src/lib/roles/desiredRoleOptions.ts) の条件（`is_it_saas`）を通す |
| 希望勤務地 | `PREFECTURE_FILTER_GROUPS`（47件） |
| 希望フェーズ | `PHASE_OPTIONS` |
| 勤務形態 | `desired_work_styles` の語彙 |
| 希望年収 | 数値。★**範囲の下限だけ言われたら下限だけ入れる**（上限を推測しない） |

⚠️★**解決できなかった語は画面に出す。黙って落とさない**（`InterpretResult.unresolved` と同じ）。
⚠️★**LLM の出力文字列を DB のパターン照合に渡さない。** 根拠は実測済みの事故
   （`'東京都' LIKE '%京都%'` が true で、掲載79社全件が「京都の企業」として返った）。

### 5-2. `worry` を使うなら読み手とセットで

`worry`（いまの悩み）は **3/10 人に値があるのに読む画面が0**（入力欄も受け口も撤去済み）。
①が最初に書き戻したくなる先だが、**「保存したのに読まない」の現存例**。
⚠️ **使うなら、どこに出すかを同時に決める。決めないなら書かない。**

## 6. LLM の呼び出し

| | |
|---|---|
| SDK | **`@anthropic-ai/sdk`**（TypeScript。公式SDK以外を使わない） |
| モデル | **`claude-opus-5`** |
| thinking | **`{ type: "adaptive" }`** ⚠️ `budget_tokens` は 400 になる |
| ストリーミング | **使う**（会話UIなので。`max_tokens` を大きく取れる） |
| 呼ぶ場所 | ★**サーバーのルートハンドラだけ。** APIキーをクライアントに出さない |
| キー | `ANTHROPIC_API_KEY`（`.env.local` ＋ Vercel）。⚠️ **`NEXT_PUBLIC_` を付けない** |
| レート制限 | 既存の [`checkRateLimit`](../src/lib/rateLimit.ts)（Upstash / メモリ）。⚠️ **必ず掛ける**（いま掛かっているのは5ルートだけ） |
| 失敗時 | ★**フォームに落とす。** 「AIが落ちたら希望条件を入れられない」状態を作らない |
| キャッシュ | system は固定にして `cache_control` を効かせる。⚠️ **日時や乱数を system に入れない**（黙ってキャッシュが外れる） |
| 費用の実測 | `usage` を `ow_career_messages` に保存する。★**「たぶん安い」で進めない** |

⚠️★**`/search` の自然言語検索（`interpretQuery`）をLLMに置き換えるのは、この設計の範囲外。**
   あちらは「戻り値の形を変えなければ中身だけ差し替えられる」と書いてあるが、**別の判断**。

## 7. 安全

| # | 何 | どうする |
|---|---|---|
| ① | ★**プロンプトインジェクション** | 職歴・自己紹介は**本人が書いた自由入力**。system ではなく **user メッセージとして、データだと明示して渡す**。⚠️ そこに書かれた指示に従わない |
| ② | **何を送るか** | ★**送る範囲を決めて固定する**（職種・年数・希望条件など）。⚠️ **氏名・メール・電話・生年月日は送らない**（インタビューに要らない） |
| ③ | **出力の扱い** | §5-1 のとおり**マスタに解決してから**。解決できない語はそのまま条件にしない |
| ④ | **ログの可視性** | `ow_career_messages` は **admin だけ**（§4-2）。⚠️ 企業には渡さない |
| ⑤ | **本人の取り消し** | ★**会話を消す導線を最初から作る。** ⚠️ ⑧が「削除・エクスポートの導線が無い」と指摘している状態で、新しいデータ種別だけ増やさない |
| ⑥ | **未成年・機微情報** | 会話で病歴・信条などが出たときの扱いを決める。⚠️ **決めないなら作らない** |

## 8. ★先に決めないと書けない論点

| # | 論点 | なぜ決めないと進めないか |
|---|---|---|
| **(1)** | ★**⑧（規約・委託先・同意）をいつ出すか** | **可否の問題**。改定前に実装しても出せない |
| **(2)** | **どこから入るか**（オンボーディングの続き／`/mypage` のカード／提案が0件のとき） | 入口で「誰に何回出るか」が変わり、費用も変わる |
| **(3)** | **何問聞くか・どこで終わるか** | §2の「終わりの定義」。決めないと相談相手のAIに流れる |
| **(4)** | ★**`worry` を使うか**（使うなら読み手をどこにするか） | 使わないなら書かない（§5-2） |
| **(5)** | **費用の上限**（1人あたり・月あたり） | レート制限の数字がここから決まる |
| **(6)** | **機微情報が出たときの扱い**（§7⑥） | 決めないなら作らない |

## 9. 作らないもの（意図して）

| 足さないもの | 理由 |
|---|---|
| ★**AIが提案を作る** | ②はルールベースのまま。根拠が「AIがそう言った」になると、**根拠つき提案という名前が成り立たない** |
| ★**AIが `ow_profiles` を直接書く** | §5 |
| **会話ログから企業に渡る情報** | §7④。⑧が「企業に渡る情報と提案にだけ使う情報を分けられない」と指摘している状態で、分けられないまま増やさない |
| **`ow_conversations` への同居** | §4-1 |
| **`/search` のLLM化** | §6。別の判断 |
| **相談相手としてのAI** | §2。別製品 |

## 10. 実装順（⑧のあと）

```
1. スキーマ2表 ＋ RLS（GRANT を配らない）
2. サーバーのルート1本（ストリーミング・レート制限・usage の保存）
3. ★マスタ解決（§5-1）— ここが本体。LLM より先に書けるし、テストも書ける
4. 会話UI
5. ★確定UI（フォームの初期値として出す）
6. 費用と充填率の実測 → §8(5) の数字を決め直す
```

⚠️★**3 を先に書く。** マスタ解決はLLMが無くてもテストできる（`engine.ts` と同じ純粋関数にできる）。
   **LLM から書き始めると、いちばん壊れやすいところが最後まで検証されない。**
