## 4. 保存先 — ★★会話を保存しない（A案 / 2026-09-21 に変更）

### 4-0. ★なぜ保存しないか —— プライバシーポリシー第3項

> **当社は、職業安定法第5条の5…に基づき、次の情報を取得しません。**
> 1. 人種、民族、社会的身分、門地、本籍、出生地…　**2. 思想および信条**　3. 労働組合への加入状況
> 利用者は、これらの情報を**プロフィール等に記載しないでください**。

⚠️★**いまは「入力欄を用意しない」ことでこれを守れている。**
   ①は**自由な会話**なので、**本人が自発的に話しうる**（転職理由として信条に触れる等）。
   **会話を保存した時点で、「取得しない」と書いた情報を取得することになる。**

⚠️★**文言では回避できない。** 「記載しないでください」と足しても、会話は入力欄ではないので
   **書かせない作りにできない。** 機微情報の検出も**完全にはできない**ので、
   できない対策を規約に書くほうが危ない。

→ ★**保存しない。** 詳細は [pending/privacy-20260921-AI.md](pending/privacy-20260921-AI.md) §4(c)。

### 4-1. 何を残し、何を残さないか

| | 残す | 残さない |
|---|---|---|
| 本人の発話・AIの応答 | — | ★**残さない**（DB にもログにも） |
| 解決した希望条件 | ✅ **本人が確定させた後だけ** `ow_profiles` / `ow_profile_desired_roles` | — |
| 回数・トークン数・モデル | ✅ `ow_career_sessions`（**本文なし**） | — |

⚠️★**`console.log` / `console.error` に会話本文を出さないこと。**
   「DB に保存しない」だけでは足りない。**Vercel のログも保存先。**
   ⚠️ エラー時に body ごと出す既定の書き方（`console.error(err)`）で漏れる。

### 4-2. 表は1つだけ（★本文を持たない）

```
ow_career_sessions            1回のインタビューの記録。★本文は持たない
  id / user_id(ow_users)
  started_at / ended_at
  turns                       -- 往復の回数
  token_input / token_output  -- ★費用の実測用（本文は要らない）
  model / prompt_version      -- 数字を後から解釈するため
  applied_at                  -- 本人が確定させた日時（null = 確定していない）
  unresolved_count            -- ★解決できなかった語の「件数」だけ（語そのものは残さない）
```

⚠️★**`ow_career_messages` は作らない**（2026-09-21 に A案へ変更して削除）。
⚠️★**`unresolved` の中身を残さないこと。** 件数だけ。
   語そのものは**本人が話した言葉**で、第3項に触れうる。
⚠️ GRANT は配らない。RLS 有効・ポリシー0本・読み書きは admin だけ
   （`ow_transitions` / `ow_proposals` と同じ形）。

### 4-3. ★会話の状態はクライアントが持つ

**サーバーはステートレス。** 毎ターン、クライアントがそれまでの履歴を送る
（Messages API 自体がもともとステートレスなので、追加の仕組みは要らない）。

⚠️★**クライアントから来た履歴を信用しない。** 使ってよいのは
   **「次の応答を生成する入力」としてだけ**。⚠️ そこに書かれた指示に従わない（§7①）。
⚠️★**履歴を検証に使わない**（「前のターンでこう言ったから」を根拠にしない）。
   書き戻しの正は**最後に本人が確定させた内容だけ**。

### 4-4. ⚠️★A案が捨てているもの（正直に書く）

| 失うもの | 影響 | 代わり |
|---|---|---|
| **リロードで会話が消える** | 中断・再開ができない | ★**画面に明記する。** 加えて**短いインタビューにする**（§2の「終わりの定義」が**必須**になる） |
| **運営が「何を聞いたか」見られない** | プロンプトの改善が実データでできない | 合成データと、**本人からの報告**。⚠️ ログを見て直す運用を前提にしない |
| **障害調査ができない** | 「何を送ったら壊れたか」が分からない | `unresolved_count` と `turns` と例外の型だけで切り分ける。⚠️★**調査のために本文を残さない** |
| **④（反応の学習）に使えない** | ①の会話は学習の材料にならない | ④の材料は**見送り理由**（`ow_proposal_declines`）のまま |

⚠️★**「あとで必要になったら保存する」にしないこと。** 保存を始めた日に第3項へ戻る。
   **必要になったら、先に規約を変える。**

### 4-5. ★`ow_conversations` には同居させない（A案でも変わらない）

構造上は `kind='editor'` に入れられるが、**入れない。**

| 理由 | |
|---|---|
| ① | そもそも**保存しない**ので、器が要らない |
| ② | `kind_check` / `kind_consistency` / `stage_consistency` / `role_check` の**4つを広げる**ことになる |
| ③ | ★**`/mypage/conversations` に人とAIの会話が混ざる** |

## 5. 出力 — ★AIが直接書かない

```
会話 ──▶ AIが「こう理解しました」を出す ──▶ ★本人が確認して押す ──▶ ow_profiles に書く
                                              ▲
                                     ここを飛ばさない
```

| なぜ | |
|---|---|
| ① | ★**本人が言っていないことを保存することになる。** このリポジトリが繰り返し戒めている「値が無いことを、ある値に置き換えない」の、いちばん大きい版 |
| ② | ②の根拠（`preference_match`）は**本人の希望を前提**にしている。推測が混ざると**提案の根拠が推測になる** |
| ③ | ★**A案では会話が残らない**ので、**確定を後回しにできない。** その場で押してもらう形にする（⚠️ だから §2 の「終わりの定義」が必須） |

⚠️★**確定の UI は「AIの文章」ではなく「フォームの初期値」にする。**
   ＝ 会話の結果を**いまある入力欄に入れた状態**で見せて、本人が直して保存する。
   **新しい保存経路を作らない**（既存の `PUT /api/jobseeker/career-preferences` などを通す）。

### 5-1. ★LLM の出力は必ずマスタに解決してから

**`interpretQuery` の約束（§C-3 ④）をそのまま適用する。**

| 引き出すもの | 解決先 |
|---|---|
| 希望職種 | `ow_roles` ＋ `ow_role_aliases`（260行）。★[`desiredRoleOptions`](../src/lib/roles/desiredRoleOptions.ts) の条件（`is_it_saas`）を通す |
| 希望勤務地 | `PREFECTURE_FILTER_GROUPS`（47件） |
| 希望フェーズ | ★**`DESIRED_PHASES`（日本語4値）**。⚠️ `PHASE_OPTIONS` の slug ではない（下の訂正） |
| 勤務形態 | `desired_work_styles` の語彙 |
| 希望年収 | 数値。★**範囲の下限だけ言われたら下限だけ入れる**（上限を推測しない） |

⚠️★**解決できなかった語は画面に出す。黙って落とさない**（`InterpretResult.unresolved` と同じ）。
⚠️★**LLM の出力文字列を DB のパターン照合に渡さない。** 根拠は実測済みの事故
   （`'東京都' LIKE '%京都%'` が true で、掲載79社全件が「京都の企業」として返った）。

#### ⚠️★訂正: 希望フェーズは日本語ラベル（2026-09-21 に実装して判明）

この節は当初「`PHASE_OPTIONS`」と書いていたが**誤り**。
`ow_profiles.desired_phase` に入るのは **`DESIRED_PHASES`＝「シリーズA」「シリーズB」
「シリーズC」「上場」の4つの日本語ラベル**で、`PHASE_OPTIONS` の slug（`series_a` など13件）
ではない。**API の検証（`VALID_DESIRED_PHASES`）もこの4値。**
⚠️ 企業の `ow_companies.phase`（slug・13値）と**別の語彙**。混ぜないこと。

### 5-2. `worry` を使うなら読み手とセットで

`worry`（いまの悩み）は **3/10 人に値があるのに読む画面が0**（入力欄も受け口も撤去済み）。
①が最初に書き戻したくなる先だが、**「保存したのに読まない」の現存例**。
⚠️ **使うなら、どこに出すかを同時に決める。決めないなら書かない。**

## 7. 安全

| # | 何 | どうする |
|---|---|---|
| ① | ★**プロンプトインジェクション** | 職歴・自己紹介は**本人が書いた自由入力**。system ではなく **user メッセージとして、データだと明示して渡す**。⚠️ そこに書かれた指示に従わない |
| ② | **何を送るか** | ★**送る範囲を決めて固定する**（職種・年数・希望条件など）。⚠️ **氏名・メール・電話・生年月日は送らない**（インタビューに要らない） |
| ③ | **出力の扱い** | §5-1 のとおり**マスタに解決してから**。解決できない語はそのまま条件にしない |
| ④ | **ログの可視性** | ★**そもそも本文を残さない**（§4-1）。`ow_career_sessions` は数だけで、**admin しか読まない**。⚠️ 企業には渡さない |
| ⑤ | **本人の取り消し** | ★**A案では「消すもの」が無い。** 残るのは**本人が確定させた希望条件**だけで、それは**既存の入力欄から本人が直せる**。⚠️ 新しい削除導線を作る必要が無いのが A案の利点 |
| ⑥ | ★**機微情報** | ★**A案の理由そのもの**（§4-0）。会話で信条・病歴に触れても、**保存しないので取得にならない**。⚠️★**検出して落とす仕組みを作らない** —— 完全にできないものを作ると、できたつもりになるほうが危ない |
| ⑦ | **未成年** | ⚠️ 年齢での出し分けは**未決**（§8(6)）。**決めないなら作らない** |

## 9. 作らないもの（意図して）

| 足さないもの | 理由 |
|---|---|
| ★**AIが提案を作る** | ②はルールベースのまま。根拠が「AIがそう言った」になると、**根拠つき提案という名前が成り立たない** |
| ★**AIが `ow_profiles` を直接書く** | §5 |
| **会話ログから企業に渡る情報** | §7④。⑧が「企業に渡る情報と提案にだけ使う情報を分けられない」と指摘している状態で、分けられないまま増やさない |
| **`ow_conversations` への同居** | §4-5 |
| ★**会話の保存** | §4-0。⚠️★**「あとで必要になったら保存する」にしないこと。** 必要になったら**先に規約を変える** |
| ★**機微情報の検出** | §7⑥。完全にできない対策を作らない |

**テストが守っているのは3つ:**

| # | 何 | 代表的なテスト |
|---|---|---|
| ① | ★**部分一致をしない** | 「東京」→ 東京都 ／「京都」→ 京都府（**取り違えない**）／「セールス」だけでは当てない |

| ③ | ★**推測しない** | 年収 `6000000` は**単位を直さず** `out_of_range` ／ 上下逆は**入れ替えず** `range_inverted` で両方落とす ／ 上限超過は**切らず** `over_limit` |
