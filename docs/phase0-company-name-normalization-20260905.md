# フェーズ0調査: 企業名の正規化にカナ・英字の揺れを入れるか

調査日: 2026-09-05 ／ **読み取りのみ。migration の作成・適用はしていない。**

---

## 0. 結論（先に）

| | |
|---|---|
| **かな畳み（ひらがな↔カタカナ・半角カナ）** | **入れてよい。ただし救う件数は今のところ小さい**（ひらがなを含む社名は100社中**2社**、半角カナは**0社**） |
| **長音「ー」を落とす** | **入れない。** 過剰一致の危険に対して得るものが釣り合わない |
| **英字 ⇔ 日本語（ANDPAD ⇔ アンドパッド）** | ★**正規化では原理的に解けない。** 別名（`brand_name` / `name_en` / `search_aliases`）を**照合の対象に足す**のが本筋 |

⚠️★**優先度は「かな畳み」より「別名を照合に入れる」のほうが高い。**
実測（下記 B-2）で、正規化が既に 100% 拾えている表記に対し、
**別名系は 0〜28% しか拾えていない。** いま重複が作られるとしたらそこ。

## A. 現在の実装

### A-1. `normalize_company_name(text)` が何をしているか

`LANGUAGE sql / IMMUTABLE STRICT / SET search_path TO 'pg_catalog'`。7段。

| # | 処理 | 例 |
|---|---|---|
| 1 | **全角英数 → 半角**（`translate`） | `ＡＢＣ１２３` → `ABC123` |
| 2 | **小文字化**（`lower`） | `ANDPAD` → `andpad` |
| 3 | **空白・記号を除去** `[[:space:]　・･.,．，‐‑‒–—―−－-]` | `セールス・フォース` → `セールスフォース` |
| 4 | **先頭の法人格を除去** 株式会社/有限会社/合同会社/合資会社/合名会社/一般社団法人/一般財団法人/(株)/（株）/㈱/(有)/（有）/㈲/(同)/（同） | `株式会社大林組` → `大林組` |
| 5 | **末尾の法人格を除去**（4 から一般社団/財団を除いたもの） | `スパイダープラス株式会社` → `スパイダープラス` |
| 6 | **末尾の英語法人格を除去** `(incorporated\|corporation\|company\|coltd\|inc\|corp\|ltd\|llc)\.?$` | `Opinio Inc.` → `opinio` |
| 7 | `nullif(…, '')` | 空になったら NULL |

**触っていないもの**: ひらがな／カタカナの相互変換、半角カナ、**長音「ー」**（U+30FC は
除去記号の集合に**入っていない** ——集合にあるのはハイフン・ダッシュ類だけ）。

実測:

```
normalize_company_name('株式会社ANDPAD')       → 'andpad'
normalize_company_name('株式会社アンドパッド')   → 'アンドパッド'      ★別物
normalize_company_name('（株）大林組')          → '大林組'
normalize_company_name('ｵｵﾊﾞﾔｼｸﾞﾐ')            → 'ｵｵﾊﾞﾔｼｸﾞﾐ'        ★半角カナは素通り
normalize_company_name('サーバーワークス')       → 'サーバーワークス'   ★長音は残る
```

### A-2. 呼んでいる場所（全数）

| 種別 | 実体 | 何のために |
|---|---|---|
| **トリガー** | `trg_ow_companies_normalized_name`（BEFORE INSERT OR UPDATE / FOR EACH ROW） → `ow_companies_set_normalized_name()` | `NEW.normalized_name := normalize_company_name(NEW.name)`。**常に name から再計算する** |
| 関数 | `find_companies_by_normalized_name(p_name)` | 重複検出（`normalized_name = normalize(p_name)`） |
| **関数** | **`can_send_scout(p_company_id, p_candidate_id)`** | ★**スカウトのブロック判定**（条件2b「自由入力の社名でも一致させる」） |
| **関数** | **`get_blocked_companies(p_auth_user_id)`** | ★同上（在籍企業の突合） |
| src | `POST /api/biz/companies` / `POST /api/jobseeker/companies` | どちらも RPC 経由。**TS 側で正規化値を作っている箇所は0件** |

⚠️★**「重複検出のためだけの関数」ではない。**
`can_send_scout` と `get_blocked_companies` が
`normalize_company_name(e.company_text) = normalize_company_name(c.name)` で
**在籍企業からのスカウトを止める判定**に使っている。
**正規化を変えるとこの判定も変わる。**

⚠️ ただし**変える方向は fail-safe 側**。緩める（より多く一致する）と
**より多くブロックする**ことになるので、勧誘してはいけない相手に送ってしまう向きには倒れない。
**逆に厳しくする変更は危険**（ブロックが漏れる）。

### A-3. `normalized_name` を読んでいる場所

**`find_companies_by_normalized_name` の1箇所だけ。**
src からの直接参照は**0件**（`types.ts` の型定義を除く）。
⚠️ `can_send_scout` / `get_blocked_companies` は**列ではなく関数を直接呼んで**比べているので、
列を読んではいない。

### A-4. ★索引と制約 → **UNIQUE ではない。作り直しで衝突しない**

```
CREATE INDEX ow_companies_normalized_name_idx
  ON public.ow_companies USING btree (normalized_name)
  WHERE (normalized_name IS NOT NULL);
```

- **UNIQUE ではない**（ただの部分索引）
- `normalized_name` を参照する **CHECK / UNIQUE / 排他制約は0本**
- **式インデックス（`normalize_company_name(...)` を式に持つ索引）も0本**
  → `IMMUTABLE` 関数の定義を差し替えても、**再構築が必要な索引は無い**

**したがって、値が重複しても INSERT / UPDATE は落ちない。作り直しは安全。**

## B. 揺れの実態

### B-1. ★現在の100社で、カナ・英字を揃えたら同一になるペア → **0件**

| 条件 | 衝突グループ数 |
|---|---|
| 現状の `normalized_name` | **0** |
| ＋ ひらがな→カタカナ を畳む | **0** |
| ＋ さらに長音「ー」も落とす | **0** |

**いま重複しているペアは1組も無い。** 正直に書く。
**これは「揺れが起きない」という意味ではなく、「まだ起きていない」という意味。**

⚠️ 検出器の自己テストを先に通した（ルール⑱）:
`translate('あんどぱっど…', ひらがな, カタカナ)` → `'アンドパッド…'` を確認してから
0件を読んでいる。**畳みが効いていないまま「0件」と読まないため。**

社名の内訳（100社）: カタカナを含む **62** ／ 英字を含む **31** ／ 長音を含む **31** ／
**ひらがなを含む 2**（合同会社やめるラボ・みずほ証券株式会社）／ **半角カナを含む 0**。

### B-2. ★求職者が入れそうな表記の一致率（掲載中83社・機械的に生成）

| 打ち方 | 試した数 | 一致 | 一致率 |
|---|---|---|---|

| ⑤ 法人格を外した形 | 83 | 83 | **100%** |
| ⑥ 全角英数で入力 | 83 | 83 | **100%** |
| ⑦ 大文字小文字を崩す | 83 | 83 | **100%** |
| ⑧ 「（株）」表記 | 83 | 83 | **100%** |
| ⑫ ナカグロ「・」を打たない | 12 | 12 | **100%** |
| **② 英語名（`name_en`）** | 79 | 22 | **27.8%** |
| **③ ブランド名（`brand_name`）** | 10 | 1 | **10.0%** |
| **④ 読み仮名（`search_aliases`）** | 28 | **0** | **0.0%** |

**★現行の正規化が担当している範囲（①⑤⑥⑦⑧⑫）は既に 100%。伸びしろは無い。**
**取りこぼしているのは ②③④（別名）と ⑨⑪（かな・長音）。**

### B-3. ★英字と日本語は正規化では解けない → `search_aliases` の実態

| | 実測（2026-09-05） |
|---|---|
| `search_aliases` が入っている企業 | **29社 / 100社**（掲載中は **28 / 83**） |
| 中身 | **カタカナの読み仮名**。`Asana Japan株式会社` → `アサナ` ／ `株式会社SmartHR` → `スマートエイチアール` |
| 使われ方 | **`ilike` の検索対象**（`/api/companies/lookup`・`/api/companies/search`・`/api/search/suggest`・`lib/search/companies.ts` の4箇所） |
| **重複検出での使われ方** | ★**無い。** `find_companies_by_normalized_name` は `normalized_name` しか見ない |

#### ★実害の正確な形（アンドパッドの例）

```
株式会社アンドパッド   brand_name='ANDPAD'  search_aliases=NULL  normalized_name='アンドパッド'
```

| 「ANDPAD」と打つと | 結果 |
|---|---|
| **企業ピッカー**（`/api/companies/lookup`・ILIKE で `brand_name` も見る） | **見つかる** ✅ |
| **重複検出**（`find_companies_by_normalized_name`・`normalized_name` のみ） | **見つからない** ❌ |

→ **ピッカーでは選べるので、いまは重複が作られにくい。**
   作られるのは「ピッカーで探さずに、いきなり登録ダイアログで別表記を打った」ときだが、
   ダイアログの重複照会も同じ RPC を通るので**同じ穴が空いている。**

⚠️ **別名は既に3列ある**（`brand_name` 10社 / `name_en` 79社 / `search_aliases` 29社）。
   **新しい列は要らない。** 足りないのは「重複照合がそれらを見ていない」こと。

## C. 作り直しの影響

### C-1. 副作用 → **`updated_at` は動かない**

`ow_companies` のトリガーは**2本だけ**。

| トリガー | 契機 | 中身 |
|---|---|---|
| `trg_ow_companies_normalized_name` | BEFORE INSERT OR UPDATE | `normalized_name` を `name` から再計算 |
| `trg_guard_company_approval` | BEFORE UPDATE | 承認・公開の切り替えを企業に許さない |

- **`updated_at` を触るトリガーは無い。** 再計算の UPDATE で `updated_at` は動かない
  （⚠️ 動くと `/companies` の「新着順」が全社入れ替わる。ここは重要）
- `guard_company_approval` は `is_approved` / `is_published` / `listing_status` が
  **変わるときだけ**弾くので、再計算では素通りする
- ほかに `ow_companies` の派生値を動かすトリガーは無い

⚠️ 再計算は **`UPDATE ow_companies SET name = name`** でも
**`SET normalized_name = normalize_company_name(name)`** でも同じ結果になる
（どちらも BEFORE UPDATE トリガーが上書きするため）。

### C-2. 100社の再計算で値が変わるのは何社か（試算）

⚠️ `normalized_name` は**照合専用で画面には出ない**ので、表記が変わっても表示に影響しない。

## D. ★正規化に足す変換の候補と判断案

| # | 変換 | 判断 | 理由 |
|---|---|---|---|
| 1 | **ひらがな → カタカナ** | **入れる** | 打ち間違いではなく**入力方式の差**（変換し忘れ）。過剰一致が起きない（音が同じものだけが一致する）。実データで衝突0。⚠️ 救う件数は今2社と小さい |
| 2 | **半角カナ → 全角カナ** | **入れる** | 同上。⚠️ 現在該当0社だが、**入力は自由文なので利用者側から来る**。`translate` では濁点の合成が扱えないので `regexp_replace` の連鎖か、素直に対応表で書く |
| 3 | **全角英数 → 半角** | **既に入っている** | 実測で一致率100% |
| 4 | **英字の大小** | **既に入っている** | 同上 |
| 5 | **ナカグロ「・」「･」** | **既に入っている** | 実測で12社とも一致 |
| 6 | **空白（半角・全角）** | **既に入っている** | — |
| 7 | **ハイフン・ダッシュ類** | **既に入っている** | `‐‑‒–—―−－-` の8種 |
| 8 | **★長音「ー」を落とす** | **★入れない** | 下記 |
| 9 | **「ヶ/ケ」「ヵ/カ」の揺れ** | **入れない** | 該当0社。増えたら考える |
| 10 | **大文字の促音・拗音（ッ↔ツ、ャ↔ヤ）** | **入れない** | 「キャノン/キヤノン」型は実在するが**該当0社**で、過剰一致（`シヤチハタ` と `シャチハタ` は同じだが、別語で衝突しうる）の判断材料が無い |
| 11 | **英字 ⇔ 日本語の対応** | **★正規化でやらない** | 下記 |

### D-1. ★長音「ー」を落とすか → **落とさない**

**得るもの**: 「打ち忘れ」を25社ぶん救える（B-2 ⑪）。

**失うもの**: 過剰一致。長音を落とすと
`コーポ` と `コポ`、`カード` と `カド`、`ミラー` と `ミラ` が**同じ値になる**。
⚠️ 実データ100社では衝突0だが、**それは母数が100しかないから**で、
**企業が増えるほど確実に衝突する方向の変換**。

**重要なのは「間違えたときにどちらへ倒れるか」**:

| | 長音を残す（現状） | 長音を落とす |
|---|---|---|
| 取りこぼし | 「打ち忘れ」が重複として作られる | 減る |
| **過剰一致** | 起きない | **別の会社を「もしかしてこれ？」に出す** |

**重複は運営が後から統合できるが、別会社を同一視した誤りは利用者の職歴に残る。**
⚠️ しかも「もしかしてこれ？」は**止めない**設計なので、
過剰一致は「押してしまう」形の事故になる。**非対称なので、残す側に倒す。**

⚠️ 打ち忘れを救いたいなら、**正規化ではなく候補提示（ILIKE / 別名）で拾う**ほうが安全。
   あちらは**候補を出すだけで確定させない**。

### D-2. ★英字 ⇔ 日本語 → **正規化でやらない。別名を照合に入れる**

`Salesforce` と `セールスフォース` は**文字列変換では絶対に結びつかない**
（音写の規則が一意に定まらない。`Sansan`→`サンサン`、`SmartHR`→`スマートエイチアール`、
`MongoDB`→`モンゴディービー` はどれも人が決めた読み）。
**正規化に足そうとすると、必ず辞書＝別名になる。**

**別名の器は既に3つある。** 新しい列は要らない。

| 列 | 入っている数 | 中身 |
|---|---|---|
| `search_aliases` | 29 / 100 | **カタカナの読み仮名**（`アサナ` `ハブスポット`） |
| `name_en` | 79 / 100 | 英語名（`Asana Japan`） |
| `brand_name` | 10 / 100 | ブランド名（`ANDPAD` `Datadog`） |

→ **やるべきは `find_companies_by_normalized_name` を「別名も見る」形に広げること。**

⚠️★**そのとき、正規化とは別の関数にすること。**
   `normalize_company_name` は `can_send_scout` / `get_blocked_companies`
   （＝**スカウトのブロック判定**）が使っている。
   **重複検出のために緩めた条件が、そのままブロック判定に効く。**
   ブロックは緩いほうが安全側なので**すぐ事故にはならない**が、
   **別々の目的を1つの関数に載せ続けると、いつか片方の都合でもう片方が壊れる。**

⚠️ 別名を照合に入れると **`アサナ` で `Asana Japan株式会社` が引ける**ようになるが、
   **一致は「完全一致」にすること。** 部分一致にすると
   「もしかしてこれ？」が候補で溢れる（それは ILIKE のピッカーの仕事）。

### D-3. 実装するとしたらの順序（★今回は実装しない）

1. **別名を重複照合に入れる**（`brand_name` / `name_en` / `search_aliases` を正規化して比較）
   —— B-2 で 0〜28% しか拾えていない**唯一の穴**
2. かな畳み（ひらがな→カタカナ、半角カナ→全角）を `normalize_company_name` に足す
   —— 救う件数は小さいが、副作用がほぼ無い（値が変わるのは2社・衝突0・冪等）
3. **長音は落とさない**
4. 変えたあと **`UPDATE ow_companies SET name = name`** で全行再計算し、
   **異なり数が100のまま（衝突0）であることと、`updated_at` が動いていないこと**を実測する
