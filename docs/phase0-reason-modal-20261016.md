## 3. 保存の形（migration の案。作っていない）

### 案A（推奨）: 回答の単位は今のまま「職歴の行」、ただし画面は「会社」で聞く

- 同じ会社の役割が複数あるときは、**その会社でいちばん古い役割の行**（＝入社したとき）に保存する
- 行のアイコンは会社の行にだけ出す。役割の追加では開かない
- 既存の回答は全部「その会社で役割が1つ」なので（§1-2）、移す行が無い
- ⚠️ 案B（会社ごとの新しい表を作る）は、自由入力の会社（回答の 4/21）でキーが作れず、職歴の削除との連動も自前で持つことになる

### 追加するもの

| # | 何を | 形 |
|---|---|---|
| ① | 選択肢の追加 | `join_reasons` の CHECK を15値に。`join_reason_primary` の CHECK はそのまま |
| ② | 新旧の区別 | `ow_experiences.reason_version smallint`（NULL＝旧の質問「選んだ理由」、2＝新の質問「期待していたこと」）。⚠️ 既存20行は NULL のまま。推測で 2 にしない |
| ③ | A: 期待への評価 | 新しい表 `ow_experience_expectations(experience_id, reason, rating smallint)`。`rating` は -2〜2（下回った〜上回った）。`reason` は CHECK で15値から `personal` を除く14値。`UNIQUE(experience_id, reason)`、`ON DELETE CASCADE` |
| ④ | B: ずれの方向 | 新しい表 `ow_experience_gap_shifts(experience_id, axis, value smallint)`。`value` は -2〜2。⚠️ **旧の `ow_experience_gaps` には書かない** |

## 4. 並べ替えへの反映（案）

### 4-1. 正直な前提

並べ替えに使うには「**その会社が◯◯をどれだけ満たすか**」という会社側のデータが要る。15項目のうち、会社側のデータがあるのは一部だけ。

| 項目 | 会社側の手がかり | 今使えるか |
|---|---|---|
| 職種・役割 | 求人の職種（`role_opening`） | ○（公開求人のある掲載企業は1社） |
| 事業・プロダクト | 事業領域（`same_domain`） | ○ |
| 顧客・業界 | 顧客の業界（軸2） | ✗（掲載21社がすべて horizontal） |
| 働き方 | `remote_work_status` | △（値が推測投入だった過去あり。出典を確かめてから） |
| 事業の成長性／知名度・安定性 | `phase` | ○ |
| 年収・待遇 | 求人の年収 | △（求人2件） |
| 上記以外（任される範囲・スキル・次のキャリア・上司・仲間・カルチャー・評価） | **その会社の在籍者の回答（A の評価）しかない** | ✗ **3人以上の会社が1社だけ。しかもそれは旧形式の回答** |

### 4-2. 案

1. **本人が今言っていること**（`next_priorities`）: 選んだ項目に会社側の手がかりがあれば、その項目のシグナルの重みを上げる（例: 「事業・プロダクト」を選んだ人は `same_domain` 30 → 45）。手がかりの無い項目は**点数に入れない**
2. **過去のデータが示すこと**（推定）: 2社以上答えている人だけ。項目ごとに「その項目の評価（-2〜2）と、合っていたか（0〜10 を 5 からの差に直す）の向きが揃った会社の数」を数え、2社以上揃った項目を「満足を左右している項目」とする
   - 例: 年収を期待して期待通り(0)で3点、カルチャーを期待して上回って(+2)9点 → カルチャーは向きが揃う、年収は揃わない
   - 相関係数のような計算は使わない（2〜3社では値が暴れる。説明もできない）
3. **2つがずれているとき**: 両方に当たる会社を最も上げる（重み × 1.5）。今言っていることだけ → × 1.0。推定だけ → × 0.5 にとどめ、並べ替えより「過去の回答では、カルチャーが満足を左右しているようです」と**本人に見せる**ことに使う（本人が `next_priorities` を直せる）
4. **1社分しかない人**: 推定はしない（向きが揃ったかを比べる相手が無い）。今言っていることだけを使う
5. **他人の回答を並べ替えに使うのは、同じ会社で新形式の回答が3人以上そろった会社だけ**（`weights.ts` の S3 と同じ線。`MIN_AGGREGATE_COUNT`）

### 4-3. 結論: 今のデータでは、保存直後に「並びが変わった会社」はほぼ出せない

- 本人の回答が並び順を動かせるのは、§4-1 の ○ の項目を `next_priorities` に選んだときだけ。モーダル（会社ごとの回答）を答えただけでは、推定が立つまで（2社以上）並びは変わらない
- したがって依頼の **§5 の1（並びが変わった会社）と2（精度のメーター）は、今の状態では出さない**のが「回答が並べ替えに実際に使われていない状態で、1と2は表示しない」に沿う
- 出せる条件: ①`next_priorities` が並べ替えに入っていること、②そのうえで本人の回答で順位が実際に動いた会社があること（保存の前後で `rankForYou` を2回計算して比べる。動かなければ出さない）

## 5. 既存回答の扱い（案）

| 何を | 案 |
|---|---|
| 旧ステップ2（3択） | **そのまま残す。** 新しい表に移さない・上書きしない。画面では「以前の回答」として見えるだけにし、新形式で答え直したら新しい表に入る |
| 旧ステップ1（選んだ理由）→ 新「期待していたこと」 | **同じ列に置くが、`reason_version` で区別する。** 読み替えの判断材料は下 |
| 名前を変えた選択肢 | 同じキーのまま表示名だけ変える（可能） |
| 集計・並べ替え | 新形式（`reason_version = 2`）だけを使う。旧形式は「決め手」として提案の根拠（`shared_motive`）にだけ残す |
| 離れた理由（7行） | 残す。新しい流れに入れるかは判断（§6） |

**「選んだ理由」を「期待していたこと」と読み替えてよいか**

- 近い: 入社理由に挙げたものは、入るときに期待していたものとほぼ重なる（「年収・待遇を理由に選んだ」≒「年収に期待していた」）
- ずれる点:
  - 「選んだ理由」は**他社と比べて決めた理由**。「期待していたこと」は比べていなくても期待していたこと全般で、範囲が広い
  - 「タイミング・個人の事情」は理由にはなるが期待ではない（新しい流れでも評価を聞かない）
  - 旧の回答には**A の評価が付いていない**ので、読み替えても並べ替えの推定（§4-2 の2）には使えない
- **推す扱い**: 回答画面の初期値として旧の選択を入れておき（本人が見直して保存したら `reason_version = 2`）、黙って読み替えない。保存するまでは旧形式のまま

## 6. 判断が必要な点

1. **回答の単位** —— 案A（会社でいちばん古い役割の行に保存。役割追加ではモーダルを開かない）でよいか
2. **「離れた理由」を残すか** —— 新しい流れに出てこない。今7行ある。案: 終了した会社だけ、ステップ2の最後に今の形のまま残す
3. **並び順の固定を破ること** —— 2026-08-19 の決めごと（以後変えない）を変える。`reason_version` で新旧を分けることで了承をもらいたい
4. **「相性の精度 ◯%」** —— Hisato 思想⑦「マッチ度%を出さない」と衝突する。正確さを測る方法も無い（答えと実際の満足を比べるデータが無い）。案: %を出さず「答えた会社 1社 / 2社 / 3社〜」の段階表示にし、「もう1社答えると、満足を左右している項目を推定できます」のように**何が起きるかを言葉で**言う
5. **D（ひとこと）を他の人に見せること** —— 今は「本人と集計にのみ使う」約束で、自由記述の表示は「集計」ではない（プライバシーポリシー4-3の対象にも理由データは載っていない）。**規約の改定が先に要る**。どこに表示するか（企業ページ？ 保存後の画面？）も未定
6. **文言「会社には伝わりません。3人以上そろったら、個人が分からない形で集計します」** —— 集計を**他の利用者に見せる**ことになる（保存後の画面の3）。プライバシーポリシー4-3（1）の情報の種類に入社理由・満足度が無いので、改定の文案が要る。5 と一緒に決めたい
7. **「相性のものさし」との関係** —— どちらも「本人が今言っていること」。両方を並べ替えに入れるか、片方にするか。並行セッションが `mypage/proposals/*` と `weights.ts` を作業中で、§4 の実装は**そのファイルと重なる**ので、着手は向こうが出し終わってから
