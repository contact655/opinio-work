# 作成時の既定値を「呼び出し側が上書きできる」形をやめる（案・未実装 / 2026-09-11）

⚠️★**案の段階。実装していない。** 方式の判断は柴さん。

## 何が起きたか

`POST /api/jobseeker/experiences` に「`visibility_company` は既存の職歴から引き継ぐ」を入れたのに、
**呼び出し側3箇所すべてが値を明示的に送っていて、その分岐に一度も到達していなかった。**

⚠️★**3箇所から外して直したが、4つ目の入口ができたらまた直書きされる。**
   原因は「**呼び出し側が既定値を送れてしまうこと**」なので、そこを塞ぎたい。

---

# 1. 方式の案（3つ）とその副作用

## 案A ── 受け取っても無視する（サーバーが常に決める）

| | |
|---|---|
| 実装 | `body.visibility_company` を**読まない**。値は常に「既存行から引き継ぐ／無ければ `real`」 |
| 良い | 壊れない。4つ目の入口ができても**値は必ず正しい** |
| ⚠️ 悪い | **静か。** 送った側は設定できたつもりになる。このリポジトリが繰り返し踏んでいる「黙って無視される」形そのもの |

## 案B ── 送られたら 400 で弾く

| | |
|---|---|
| 実装 | `"visibility_company" in body` なら 400 |
| 良い | **うるさい。** 4つ目の入口がコピーで作られたら**その場で落ちる** |
| ⚠️ 悪い | ★**デプロイ直後に、古い JS を開いたままの利用者が職歴を追加できなくなる**（400）。窓は短いが、失敗の内容が「職歴を追加できない」なので重い |

## 案C ── 型から外す（＋ サーバーは無視）

| | |
|---|---|
| 実装 | `lib/experiences/createExperience.ts` に **`CreateExperienceBody`**（`visibility_company` を**持たない**型）と `postExperience(body: CreateExperienceBody)` を置き、**入口はこれだけを使う** |
| 良い | ★**4つ目の入口が `visibility_company` を足すと、TypeScript の余剰プロパティ検査でビルドが落ちる。** `EXPERIENCE_EDITOR_COLS` で採ったのと同じ「型で気づかせる」形 |
| ⚠️ 悪い | **余剰プロパティ検査はオブジェクトリテラルにしか効かない。** `Record<string, unknown>` を組み立ててから渡すと**素通りする**（いまの職歴エディタがまさにその形）。**ヘルパーを経由しない4つ目**も止められない |

### ⚠️ 型だけでは足りない理由（`EXPERIENCE_EDITOR_COLS` との違い）

あちらは**「列を足したら SELECT にも足す」を1箇所にまとめた**もので、
**列リストが1つしかない**から効いた。こちらは**呼び出し側が3つ以上ある**ので、
**型はヘルパーを使った人にしか効かない。**

# 2. ★推奨 ── **C ＋ A**（型でビルド時に気づかせ、サーバーは常に正しい値にする）

| 層 | 何をするか |
|---|---|
| クライアント | `postExperience(body: CreateExperienceBody)` を**唯一の作成の入口**にする。型に `visibility_company` が無いので、足すとビルドが落ちる |
| サーバー | `body.visibility_company` を**読まない**。⚠️ ただし**送られてきたら `console.warn` を出す**（黙って無視しない） |

⚠️★**B（400）は採らない。** デプロイ直後の古いクライアントが職歴を追加できなくなる。
   ⚠️ ただし**警告ログで気づける**なら、あとから 400 に締めることはできる。**順序は A → B。**

⚠️ **更新（PUT）は今までどおり `visibility_company` を受ける。**
   本人が `/mypage/settings` で変える経路が正で、職歴の編集でも既存値を持ち回る必要がある。
   **作成時に受け付けないだけで、変更できなくなってはいけない。**

# 3. ★同じ形が他の列にも無いか（調査のみ。**直していない**）

**形の定義**: 呼び出し側が既定値を明示送信していて、**サーバー側の `?? 既定` が一度も発火しない**。

## `POST /api/jobseeker/experiences`

| 列 | サーバーの既定 | 呼び出し側 | 発火するか | 実害 |
|---|---|---|---|---|
| `visibility_company` | 引き継ぎ／`real` | ~~3箇所が送っていた~~ → **外した** | **する**（修正後） | ★**あった**（修正済み） |
| **`visibility_reason`** | `?? true` | 職歴エディタが **`addDraft.visibilityReason`**（`EMPTY_DRAFT` = `true`）を常に送る | ★**しない** | **いまは無い**（どちらも `true`）。⚠️ ただし**入力欄は 2026-08-16 に撤去済み**で、常に `true` が送られる。`visibility_company` と**まったく同じ構図** |
| `is_current` | `?? false` | 両方が送る | しない | 無い（**本人の入力値**なので送るのが正しい） |
| `display_order` | `?? 0` | エディタは `stints.length`、オンボーディングは送らない | 片方で**する** | 無い（意図どおり） |
| `visibility_salary` | `?? false` | **誰も送らない** | **する** | 無い |
| `prefecture` / `remote_work_status` | `parseReasonFields` が `null` | エディタが `d.prefecture \|\| null` を送る | しない | 無い（**両側とも `null`** で一致） |

## `PUT /api/jobseeker/experiences/[id]`

| 列 | サーバーの既定 | 実害 |
|---|---|---|
| ★**`visibility_company`** | **`isBlank(...) ? "real"`** | ⚠️★**いまは職歴エディタが既存値を持ち回るので無事。** ただし**送らない PUT が1つできた瞬間、伏せている人が `real` に戻る。** 既定が**広いほうに倒れている**（CLAUDE.md「公開範囲の既定を広いほうにしない」） |
| `visibility_reason` | `?? true` | 同じ形。入力欄が無いので常に `true` |

⚠️★**PUT の `?? "real"` は、作成側を直しても残る。** 方式を決めるときに**一緒に扱うこと。**
