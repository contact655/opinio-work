**業界ごとの素朴な合算（参考値）**

#### ⚠️ 落とし穴（実データで既に踏んでいる）

**同一ユーザー・同一業界で期間が重なっているペアが 3組ある。**

```sql
-- 重なりの検出（実行済み・3件）
... a.started_at <= b.ended and b.started_at <= a.ended
```

**単純合算すると経験年数が過大に出る。**「建設業界8年」と言い切るなら、

   **日単位の精度は無い。** 「8年」と出すなら年単位に丸めること。

## C. 突合クエリが書けるか

### C-1. クエリは書ける（実行可能・SELECT のみ）

```sql
-- 「その人の業界」×「企業の対象業界」
with me as (
  select distinct i.slug as industry_slug, i.name as industry_name
  from ow_experiences e
  join ow_companies  c on c.id = e.company_id
  join ow_industries i on i.id = c.industry_id
  where e.user_id = $1                       -- ow_users.id
),
target as (
  select t.id, t.name, unnest(t.market_industry_focus) as focus
  from ow_companies t
  where t.listing_status = 'listed'
    and coalesce(t.is_test,false) = false
    and t.market_industry_focus is not null
)
select target.id, target.name, me.industry_name as reason_industry
from target
join me on me.industry_slug = target.focus;  -- ⚠️ 語彙が一致していないので今は繋がらない
```

**企業マスタに解決できないので業界に結びつかない**（想定どおり）。

**「from が建設業界」の行は 0行。** そもそも建設業界の在籍者が0人なので当然。

### D-3. 業界単位で「N人が移った」を出すために足りないもの

1. **母数**。5行では、どの業界ペアも n=1〜4 にしかならない。
   ⚠️ `/search` は既に `MIN_AGGREGATE_COUNT`（3人）未満は件数も出さない方針。**同じ下限を守るなら、ほぼ全部出せない。**
2. **非ITの在籍データ**。`from_industry` が全部 IT なので、「建設 → SaaS」は1件も作れない。
3. **自由入力の会社を業界に寄せる手段**。`from_company_text` は業界に結びつかない。
   建設会社はマスタに無いので、**建設出身者が登録するほど `unknown` が増える**構造。
4. **洗い替えの運用**。`rebuild_ow_transitions()` は**手動のみ**（cron もトリガーも無い）。
   職歴が増えても、誰かが叩くまで数字は古いまま。

## E. `/search` への差し込み位置

### E-1. 現在の責務分担と、プロフィール参照の有無

| ファイル | 責務 |
|---|---|
| `src/lib/search/interpretQuery.ts`（828行） | **自然文 → マスタの ID に解決済みの条件**。ルールベース。解決先は6つ（職種 / 事業領域 / 外資 / 年収 / 社名 / スキル / 言語） |
| `src/lib/search/runSearch.ts`（753行） | **条件 → 企業 / 求人 / 人 を引く**。条件どうしは AND |
| `src/app/(jobseeker)/search/page.tsx` | 認証・ログ・0件時の緩和提案・描画 |

⚠️★**どちらも閲覧者のプロフィール（職歴）を一度も読んでいない。**
   `runSearch(conditions, isLoggedIn)` の第2引数は **boolean 1つだけ**で、
   使い道は「人の個票を返すかどうか」のマスクのみ（`runSearch.ts:412, 556`）。

```ts
export async function runSearch(conditions: Condition[], isLoggedIn: boolean): Promise<SearchResults>
```

→ **職歴を条件に使うのは、この層にとって新しい責務。** 引数を1つ足す設計変更になる。

### E-2. 戻り値の型をどう変えることになるか

**`InterpretResult` を壊さずに足せる。** 現在の型:

```ts
export type InterpretResult = {
  primaryKind: SearchKind;
  conditions: Condition[];
  unresolved: string[];
  normalized: string;
};
```

推奨する形（**文章での案。実装はしていない**）:

1. **`interpretQuery` は変えない。** ここは「検索語 → 条件」の層で、職歴は検索語ではない。
   ⚠️ ここに職歴を混ぜると、**チップに出す `label` の出どころが2つになる**
      （現在の約束②「label はマスタ側の名前から作る」が崩れる）。
2. **職歴由来の条件は別の関数で作る。** 例: `profileConditions(owUserId): Promise<Condition[]>`。
   返すのは既存の `Condition` と**同じ型**にする（`runSearch` の当て方を変えずに済む）。
3. **`Condition` に出どころを1つ足す。**
   ```ts
   origin: "query" | "profile"     // 既定は "query"
   ```
   画面はこれを見て「あなたの職歴から」と**チップの見た目を分ける**。
   ⚠️ **混ぜて1つの塊にしないこと。** 利用者が外せるのは自分が打った条件で、
      職歴由来の条件は「外す」ではなく「なぜ出たか」を説明する対象。
4. **`runSearch` は第3引数で受ける**: `runSearch(conditions, isLoggedIn, profileConditions)`。
   ⚠️ **AND に混ぜない。** 混ぜると、職歴を持つ人だけ結果が減る
      （既存の「条件どうしは AND」の意味が閲覧者ごとに変わる）。
      **並び順の加点**か、**別の帯（「あなたの業界の経験が活きる会社」）**として出す。

### E-3. 未ログイン時の扱い

現在の分岐（`search/page.tsx:303, 379` / `runSearch.ts:412`）:

| | 未ログイン | ログイン中 |
|---|---|---|
| 人の個票 | **返さない**（`items` は空） | 返す |
| 人の件数 | `MIN_AGGREGATE_COUNT`（3）未満なら**出さない** | 出す |
| 企業・求人 | 制限なし | 制限なし |

**この機能は職歴が前提なので、未ログインでは成立しない。** 噛み合わせ方は2つ:

- **A案（推奨）**: 未ログインでは**帯ごと出さない**。既存の分岐に手を入れない。
  ⚠️ 「ログインすると見られる」の案内を出すかは別の判断（人検索は既に出している）。
- **B案**: 未ログインでも帯の枠だけ出して中身を伏せる。
  ⚠️ **人検索の下限（3人）とは性質が違う。** あちらは**個人の特定**を避けるための下限で、
     こちらは企業の話なので伏せる理由が無い。**同じ仕組みを流用しない。**

⚠️ どちらにせよ、**職歴0件のログインユーザー**（実測2人 / 8人中）でも成立しない。
   「ログインしているか」ではなく「**職歴があるか**」で出し分けること。

### E-4. `force-dynamic` と `ow_search_logs` への影響

| | 現状 | この機能を足したとき |
|---|---|---|
| レンダリング | `export const dynamic = "force-dynamic"`（`search/page.tsx:40`） | **影響なし**。既に閲覧者ごとに変わる前提 |
| キャッシュ | `runSearch` は**意図的にキャッシュしない** | **影響なし** |
| ログ | `ow_search_logs`（**2行**）に `query / primary_kind / conditions(jsonb) / unresolved / result_count / user_id` | ⚠️ **下記** |

⚠️★**`conditions` は jsonb なので `origin` を足しても DB は壊れない。** ただし2点:

1. **`primary_kind` には CHECK がある**（`ow_search_logs_primary_kind_check`・3値）。
   帯を新しい「対象」として数えたくなっても、**`SearchKind` を増やすと CHECK に当たる**。
   `searchLog.ts:25` に「値を足すときは migration の CHECK と `SearchKind` も同時に直す」と明記されている。
2. **`result_count` は `results[primary].total` 1本。** 帯の件数はここに入らない。
   帯の当たり具合を見たいなら**列を足す判断**が要る（今は入れないほうがよい。2行しかない）。

⚠️ 連打除け（`DEDUPE_WINDOW_MS = 10秒`）はプロセス内 Map。**閲覧者ごとの条件が増えても壊れない**
   （キーに `user_id` が入っている前提を確認すること）。
