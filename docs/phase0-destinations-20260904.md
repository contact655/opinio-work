## 0. 結論（先に書く）

**いま画面を作れない。データを増やす方が先。**

- 「出発点 → 現在地」のペアが作れるのは **3人**。
- そのペアを「出発点(業種 × 職種)」でグルーピングすると、**最大のグループが 1人**。
- しきい値10件を満たす組み合わせは **0件**。しきい値を **1** まで下げれば「成立」するが、
  そのとき各グループは1人なので、**画面に出る「行き先」は特定の個人の職歴そのもの**になる。
- さらに3件のうち **1件は出発点と現在地が同一企業・同一職種**（社内の職種変更のみ）で、
  「移った人」として出せる実質的なペアは **2件**。

## 5. クエリの実現性

### 5-1. SQL 1本で引けるか → **引ける**

§2 の集計は以下1本で取得した（実行済み・結果は §2 のとおり）。

```sql
with real_u as (
  select id from ow_users
   where coalesce(is_test,false)=false
     and coalesce(is_system,false)=false
     and coalesce(visibility,'') <> 'private'
),
e as (
  select ex.id, ex.user_id, ex.started_at, ex.ended_at, ex.is_current,
         coalesce(i.name,'(業種なし)')            as ind,
         coalesce(r.name,'(職種なし)')            as role_child,
         coalesce(rp.name, r.name, '(職種なし)')  as role_top,
         coalesce(ex.ended_at, current_date) - ex.started_at as dur
    from ow_experiences ex
    join real_u u        on u.id  = ex.user_id
    left join ow_companies  c  on c.id  = ex.company_id
    left join ow_industries i  on i.id  = c.industry_id
    left join ow_roles      r  on r.id  = ex.role_category_id
    left join ow_roles      rp on rp.id = r.parent_id
),
-- 出発点: 最も古い在籍（最長在籍にするなら order by dur desc に差し替えるだけ）
first_e as (select distinct on (user_id) * from e order by user_id, started_at asc, id),
cur_e   as (select distinct on (user_id) * from e
             where is_current or ended_at is null
             order by user_id, started_at desc, id)
select f.ind as from_industry, f.role_child as from_role,
       cu.ind as to_industry,  cu.role_child as to_role,
       count(*) as n
  from first_e f
  join cur_e  cu using (user_id)
 where f.id <> cu.id           -- 出発点と現在地が同一在籍の人を除外
 group by 1,2,3,4
 order by n desc;
```

注意点（実装するなら踏む箇所）:

- **現職が複数ある人がいた場合の tie-break が要る。** 現在の実データでは6人とも現職1件だが、
  `is_current` は複数 true になりうる（DB に制約は無い）。上の SQL は `started_at desc` で
  1件に絞っている。
- **`ended_at IS NULL` と `is_current` は現データでは完全に一致する**（実測: 6人とも両方1件）。
  片方だけを見ても今は同じ結果になるが、一致する保証は無い。
- `role_category_id` には**親カテゴリの UUID が入りうる**（実測2件）。
  `rp.name` が NULL のときに `r.name` へ落とす `coalesce` が必須。

### 5-2. `ow_transitions` を流用できるか → **できない**

| 項目 | 実測 |
|---|---|
| 行数 | **5** |
| `from_company_id` が NULL の行 | **1**（自由入力の企業からの遷移） |
| `industry_change` の内訳 | `unchanged` 4 / `unknown` 1 / `changed` **0** |
| `role_change` の内訳 | `changed` 4 / `unchanged` 1 |

理由は依頼書の前提どおり **隣接ペア（A→B）しか持っていない**ため。
A→B→C の人の「A→C」を作るには `user_id` で自己結合して連鎖を辿る必要があり、
その連鎖の再構成は結局 `ow_experiences` を直接読むのと同じ処理になる。

加えて `ow_transitions` は**手動洗い替え**（`rebuild_ow_transitions()`。cron もトリガーも無い）
なので、鮮度が `ow_experiences` と一致する保証が無い。
**別集計（§5-1 のクエリ）が要る。**

### 5-3. 実行に必要な権限

| テーブル | anon SELECT | authenticated SELECT | RLS | 読み取りポリシー数 |
|---|---|---|---|---|
| `ow_experiences` | **列単位で付与あり**（必要6列とも true） | 同左 | 有効 | 3 |
| `ow_users` | 列単位（`is_system` は **anon から落ちている**） | 必要列すべて true | 有効 | 3 |
| `ow_companies` | true | true | 有効 | 4 |
| `ow_industries` | true | true | 有効 | 2 |
| `ow_roles` | true | true | 有効 | 1 |
| `ow_user_educations` | **false** | true | 有効 | 2 |
| `ow_schools` | true | true | 有効 | 1 |
| **`ow_transitions`** | **false** | **false** | 有効 | **0** |

判定:

- **anon（未ログイン）では引けない。**
  `ow_experiences` の読み取りポリシーは `ow_experiences_public_read`
  （`ow_users.visibility = 'public'` が条件）と `ow_experiences_login_only_read`
  （`auth.uid() IS NOT NULL` が条件）の2本。**`public` のユーザーは0人**なので、
  未ログインでは **0件** が返る。
  加えて `ow_users.is_system` が anon の列 GRANT から落ちているため、
  除外条件に `is_system` を入れると **クエリごと 403** になる。
- **authenticated（ログイン中）なら引ける。**
  `ow_experiences_login_only_read` が `visibility_company <> 'hidden'` かつ
  `visibility IN ('public','login_only')` の行を通す。
  実ユーザーの職歴15件は **全件 `visibility_company = 'real'`** なので、1件も落ちない。
  依頼の前提（ログイン済みユーザーに出す）とは整合する。
- **`ow_transitions` は admin（service_role）専用。** GRANT が無く、ポリシーも0本。
- **`ow_user_educations` は anon 不可**（§4 の学校切り口を未ログインに出す場合は admin が要る）。
