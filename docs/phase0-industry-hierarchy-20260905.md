## A. `parent_id` の現状

### A-1. 実データ → **全件 NULL**

| | |
|---|---|
| `ow_industries` 全件 | **23**（有効 **21** ／ 無効2 = `realestate-construction` / `internet-web`） |
| `parent_id` が入っている行 | **0件** |

### A-2. `parent_id` を読んでいる箇所 → **0件**

- **src**: `ow_industries.parent_id` を読むコードは**存在しない**。
  `INDUSTRY_OPTION_COLS = "id, name, slug, description"` に入っていない。
  `/biz/company/page.tsx` は自前で `"id, name, slug, display_order"` を引き、
  コメントに「⚠️ `parent_id` は取らない。…**階層を戻すときに一緒に足すこと**」と書いてある
- **関数・ビュー・RLS**: 0件（`20260825110000` の冒頭で実測済みと記録）
- **migration**: baseline（索引と FK の定義）と `20260825110000_rebuild_ow_industries.sql` のみ

⚠️ 他ファイルの `parent_id` ヒットは **`ow_company_departments`** と **`ow_roles`** で、別テーブル。

### A-3. 制約 → **親子を作る準備は既に全部ある**

```
ow_industries_name_parent_id_key : UNIQUE NULLS NOT DISTINCT (name, parent_id)
ow_industries_parent_id_fkey     : FOREIGN KEY (parent_id) → ow_industries(id) ON DELETE RESTRICT
ow_industries_slug_key           : UNIQUE (slug)
ow_industries_parent_idx         : INDEX (parent_id, display_order)
```

何が制約されるか:

- **同じ親の下で名前は重複できない。** `NULLS NOT DISTINCT` なので
  **トップレベル同士（parent_id が NULL）でも重複できない**。
  ⚠️ 逆に、**親が違えば同名の子を置ける**（各親の下に「その他」を作れる）。
  `20260825110000` のコメントに「将来サブ業種を作ったとき、各親の下に『その他』を
  置けるように (name, parent_id) で持つ」と、**この用途を想定して張ったと書いてある**
- ⚠️★**`slug` はグローバルに UNIQUE。** 子の slug も**全体で一意**にする必要がある
- ⚠️ `ON DELETE RESTRICT` なので、**親を消す前に子を消す**。
  1文で全削除しようとすると必ず失敗する（`20260825110000` が実際に踏んで注記を残している）

| ④ | ★**旧110行のうち実際に使われていたのは5件だけ**（SaaS 66 / ハードウェア 8 / SIer 6 / その他(IT) 2 ＝ 82社）。**残り105行は0社の死蔵** |

UI 側（`CompanyEditClient.tsx`）のコメント:

> **常に空で常に disabled** の死んだ入力欄になっていた。**階層を戻すまで2段に戻さないこと。**

★**「階層はやめた」ではない。「中身が空だから畳んだ」であり、戻す前提で書かれている。**

### C-3. 業種を引いている絞り込み → ★**突合は1箇所だけ**

| 何が | 業種（`ow_industries`）を引くか |
|---|---|
| `?industry=` / `/companies` の絞り込み / LP のファセット | ❌ **引かない。** あれは**事業領域**（`ow_business_domains`）の slug |
| `/jobs` の絞り込み | ❌ 同上 |
| ヘッダー検索・サジェスト | ❌ |
| `lib/companies/publishable.ts` | △ **存在チェックだけ**（`industry_id` が NULL でないか） |
| **`lib/companies/industryMatch.ts`** | ✅ ★**ここだけが突合に使っている** |

`industryMatch` の突合はこの1行:

```ts
.from("ow_company_target_industries").select("industry_id, company_id")
.in("industry_id", industryIds)   // industryIds = 本人の出身業種（祖先展開なし）
```

→ **祖先展開を足す必要があるのは、この `industryIds` を作るところだけ。**

⚠️★**上（祖先）にだけ広げる。** 本人が `電機・機械` なら `{電機・機械, 製造業}` に広げ、
   「製造業向け」の企業に当たるようにする。
   **逆（本人が親『製造業』のとき子『電機・機械』向けの企業に当てる）はやらない。**
   本人が化学出身かもしれないのに、機械向けの企業を出すことになる
   ——`ow_roles` で「兄弟を拾わない」ために決めた規則と同じ。

### C-4. ★軸1と軸2で「親を選べる／選べない」を変えるか — 意見

**変えなくてよい。両方とも親を選べてよい。** ただし**理由が非対称**なので書き残す。

| | 親を選べるべきか | 理由 |
|---|---|---|
| **軸2（対象業界）** | ★**必須。選べないと止まる** | 「製造業向け」としか言えない会社が実在する。**クアルコムジャパンが実際にこれで未確認のまま止まっている**（軸2 = NULL・掲載中）。子を1つ選ばせると嘘になり、3つ全部選ばせるのは「業界を問わない」＝ horizontal と区別がつかなくなる |
| **軸1（自社の業種）** | 選べてよいが、**UI では子を勧める** | 下記 |

★**「本人側を祖先展開する」設計にすると、軸1で子を選ぶほうが**利用者にとって**常に得**になる:

```
本人が 電機・機械（子）  → {電機・機械, 製造業} に展開 → 両方の企業に当たる
本人が 製造業（親）      → {製造業} のまま           → 製造業向けの企業にしか当たらない
```

**つまり「親を選ぶと損をするが、壊れはしない」。**
だから**禁止する必要がない**——分からない人は親のまま進めてよい。
`ow_roles` が実際にそうなっている（経歴26件中11件が親直）。

⚠️ **UI で子を勧めるのは必要。** `RolePicker` と同じ「親チップ → 押すと子が開く」形にする。
   ただし業種は**単一選択**なので、職種のチップUIをそのまま流用はできない。

### D-2. 既存企業の付け替え → ★**不要**

親は**空の器**（どの企業も親を直接指さない）でよい。子に紐づく企業はそのまま。

| 子になる候補 | 業種として使っている企業 | 対象業界として使われた件数 |
|---|---|---|
| 電機・機械 | **0** | 0 |
| 素材・化学 | **0** | 0 |
| 食品・飲料 | 1（未掲載） | 0 |
| 電子機器・半導体 | 7（掲載7） | 0 |

**付け替えの対象になる行は1件も無い**（`ow_company_target_industries` 側も4値とも0件）。

#### ⚠️★ただし、それだけでは突合は繋がらない

現状のコードは `.in("industry_id", 本人の業種)` で、**祖先展開が無い**。

```
本人 = 電機・機械 の企業の出身者
企業 = 対象業界に「製造業」を持つ（クアルコム）
→ 現状: industryIds = [電機・機械] なので **当たらない**
→ 祖先展開後: [電機・機械, 製造業] なので **当たる**
```

**「付け替えは不要」だが「コードを足さないと繋がらない」。** ここを混同しないこと。

## E. 実装フェーズで最初に決めるべき論点（3つ）

### ① 見出しに何を出すか — ★これが一番厄介

`industryMatch` は **対象業界（企業側）の id でブロックを組み立てている**:

```ts
const key = row.industry_id;      // ← 企業が持つ対象業界
byIndustry.get(key).push(...)     // 見出しと年数はこのキーで決まる
```

祖先展開すると、**電機・機械 出身の人に「製造業の経験が活きる会社」という見出しが出る。**
年数の行（`あなたの職歴から（◯◯ N年）`）も**本人が持っていない業種名**になる。

- **案A**: 見出しは**本人の業種**にする（`電機・機械の経験が活きる会社`）。
  ⚠️ 同じ企業が複数のブロックに出うる
- **案B**: 見出しは**当たった対象業界**のまま（`製造業の…`）。
  ⚠️ 年数の計算を親に畳む必要がある
- **案C**: 親に当たったブロックだけ見出しを親にする（いまの実装に近い）

### ② 電子機器・半導体を「製造業」の子にするか

**掲載中7社が動く唯一の値。** 子にすると、その7社の出身者が
「製造業向け」の企業に当たるようになる（クアルコム＝当のその7社の1つでもある）。

⚠️ 子にしないと、**製造業の親を作っても実データがほぼ動かない**
（残り3値に紐づくのは未掲載1社だけ）。

### ③ 軸1のUIをどう変えるか（4画面ある）

C-1 の4画面すべてが**単一の `<select>`**。階層にすると:

- **最小案**: `<optgroup>` で親を見出しにし、**子だけを選択肢にする**（親は選べない）
- **`RolePicker` 案**: 親チップ → 子が開く。**親のままでも選べる**（職種と同じ）

⚠️ C-4 のとおり**親を選べても壊れない**（損をするだけ）ので、
**最小案（optgroup）から始めて、迷いが出たらチップへ**でよいと考える。
⚠️ ただし `<optgroup>` で親を選べなくすると、**「製造業」としか言えない人が詰まる**。
   軸2は必ず親を選べる必要があるので、**軸1と軸2でUIが分かれる**ことになる。

## F. ✅ 実装した（2026-09-05 / フェーズ1）

### F-1. マスタ（`20260905180000_industry_hierarchy_manufacturing.sql`）

「製造業」（slug `manufacturing`）を親として新設し、既存4値を子にした。
**有効22件 = トップ18 + 子4。** 既存企業の `industry_id` は**1件も付け替えていない**。

```
1  IT・ソフトウェア
2  製造業                    ← 新設（企業0社の器）
   └ 電子機器・半導体（7社）
   └ 電機・機械（0社）
   └ 素材・化学（0社）
   └ 食品・飲料（1社）
3  通信 … 18 その他サービス   ← ★17値の相対順は不変
```

⚠️ `display_order` は **親ごとの相対順**（`ow_roles` に倣った。実測で roles は
   親1〜18／子は親の中で0〜26）。**フラットに `order("display_order")` すると親子が混ざる。**
   実際、`GET /api/industries` の生の並びは
   `IT・ソフトウェア → 電子機器・半導体 → 電機・機械 → 製造業 → 通信 → 素材・化学 …` になる。
   **必ず `flattenIndustryOptions` か `IndustrySelectOptions` を通すこと。**

⚠️ migration の事後チェックで「17値の相対順が変わっていないこと」を機械的に確かめている。

### F-2. 祖先展開（[lib/companies/industryTree.ts](../src/lib/companies/industryTree.ts) 新設）

**`ow_roles` の `expandWithAncestors` は流用しなかった。** 検討した2案:

| 案 | 内容 |
|---|---|
| 案1 共通化 | `{ byId: Map<string, {id, parentId}> }` を受ける汎用関数にする。**技術的には可能** |
| **案2 別関数（採用）** | 業種用に持つ |

★理由は**型ではなく規則**。両者は**どちら側を展開するかが逆**:

| | 展開する側 |
|---|---|
| 職種（`ow_roles`） | **求人側**（本人側は自分と親までしか見ない） |
| **業種（今回）** | ★**本人側**（企業の対象業界は展開しない） |

同じ関数を import できる状態にすると、次に触る人が
「職種と同じだから企業側も展開しよう」と書ける。**別に持てば書けない。**

⚠️ 企業側を展開すると**兄弟に広がる**——「電子機器・半導体向け」の企業に
   **電機・機械** 出身の人が当たってしまう。実測で当たらないことを確認済み（F-4）。

### F-3. 見出しは本人の業種（案A）＋ 重複排除

`industryMatch` のグループ化キーを、**企業側の対象業界 → 本人が申告した業種**に変えた。

| | |
