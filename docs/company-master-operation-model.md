## 1. 確定: 出所（source）概念

企業マスタ（`ow_companies`）への行の追加経路は **2種類**。

| 出所ラベル | 意味 | 追加者 |
|-----------|------|--------|
| `admin_seed` | ADMIN が情報収集・登録したレコード（企業側からの申請なし） | ADMIN |
| `self_serve` | 企業が自らセルフサーブで作成したレコード | 企業 admin |

**重要な設計原則:**

- データ構造は出所に関わらず **同一テーブル同一行**。出所ラベルはカラム1つで表現する（後述 §3 参照）。
- 出所の違いはデータの持ち方ではなく、**ADMIN の編集権限の重みと責任帰属**の違いとして現れる。
  - `admin_seed` の行は ADMIN が正確性に責任を持つ。
  - `self_serve` の行は企業が正確性に責任を持つ（ADMIN は誤り是正時のみ介入）。

## 2. 確定: 操作マトリクス

| 操作 | self_serve の行 | admin_seed の行 |
|------|----------------|----------------|
| **作成** | 企業 admin が自ら作成 | ADMIN が作成 |
| **通常編集** | 企業 admin がドラフト方式で編集（`draft_data` 哲学準拠）。公開前に ADMIN レビューが入る想定 | ADMIN が自由に編集 |
| **誤り是正（live 介入）** | ADMIN のみ。記録必須（§4 参照） | ADMIN が自由に編集 |
| **停止（非表示化）** | ADMIN のみ | ADMIN のみ |
| **物理削除** | **設計に含めない** | **設計に含めない** |

### 物理削除を運営モデルに含めない理由

「削除したい」という要望の実体は「一般ユーザーに見えなくする」であり、`status` 操作（停止）で達成できる。物理削除は：

- 経歴等からの参照が残留している場合にデータ整合が壊れる
- 監査ログが消滅する（§4 の思想と相反する）
- 「事後モデレーション」の北極星原則（企業の発信を尊重しながら運営が管理する）と相反する

**物理削除機能は設計しない。**

### ドラフト方式との整合

既存の `draft_data`（JSON カラム）による下書き思想を self_serve にも適用する。

- 企業 admin の編集は `draft_data` に蓄積され、公開承認時に本体カラムに反映される
- 下書き段階では監査ログを記録しない（公開時1回のみ記録）
- ADMIN の live 介入は下書きを経ず直接本体を変更し、**必ず記録する**

## 3. 確定: claim を見越したデータモデル設計（案）

> migration はしない。本 section は**将来のスキーマ設計案**として明記する。

### ow_companies に持たせる出所 / claim 関連カラム

| カラム名（案） | 型 | nullable | デフォルト | 意味 |
|------------|-----|---------|----------|------|
| `source` | `text` | YES | `'admin_seed'` | 出所ラベル。値: `'admin_seed'` / `'self_serve'` |
| `claimed_company_id` | `uuid` | YES | NULL | self_serve 企業の `ow_company_admins` 側の企業 ID（claim 完了後に紐付ける FK 候補） |
| `claimed_at` | `timestamptz` | YES | NULL | claim が承認された日時 |
| `claimed_by` | `uuid` | YES | NULL | claim を承認した ADMIN の auth.users.id |

> **注**: 上記はカラム案であり、実際の migration 時に要件に応じて調整する。claim フローの実装仕様（トリガー・承認 UI 等）は本書の範囲外。

### admin_seed と self_serve の紐付け関係の表現

- `admin_seed` の行は `claimed_company_id = NULL` / `source = 'admin_seed'` の状態で存在。
- 企業が claim を申請し、ADMIN が承認すると：
  - `source` = `'admin_seed'` のまま（あるいは `'self_serve'` に変更するかは未定 → §5 参照）
  - `claimed_company_id` に申請企業の ID を書き込み
  - `claimed_at` / `claimed_by` に審査情報を記録
- この設計により、将来の claim フローが「このレコードを誰が所有しているか」を表現できる。

### データモデルが表現できる範囲（本書のゴール）

本書は「データが将来の claim フローを**表現できる形**にする」ことを目的とする。以下は本書の範囲**外**：

- claim 申請フロー（UI・メール通知・ステータス遷移）
- claim 承認フロー（ADMIN ダッシュボードでの操作）
- 申請 → 承認のトリガー実装

## 4. 確定: 監査ログで権限の緩さを担保する思想

### 基本方針

「self_serve 企業の行に ADMIN がいつでも介入できる」という権限設計は一見ルーズに見える。これを補うのが**監査ログ（変更履歴の記録）**という思想。

> ADMIN の介入権限を事前に細かく制限するより、  
> 介入の事実を必ず記録することで事後的に検証可能にする。

### 記録する情報（概念）

| 項目 | 内容 |
|------|------|
| `timestamp` | 変更日時 |
| `actor_type` | `'ADMIN as moderator'` / `'company_admin as owner'` のいずれかを区別 |
| `actor_id` | 変更者の auth.users.id |
| `company_id` | 対象企業の ow_companies.id |
| `changed_fields` | 変更されたフィールド（詳細度は §5 の保留論点） |
| `permission_context` | どの権限文脈で変更が行われたか（例: `'admin_correction'` / `'self_serve_publish'`） |

### ドラフト方式との整合

- 企業 admin の**下書き編集**: 記録しない（公開操作時1回のみ記録）
- 企業 admin の**公開操作**: 記録する（`actor_type = 'company_admin as owner'`）
- ADMIN の**live 介入**: 記録する（`actor_type = 'ADMIN as moderator'`）
- 記録の非対称性は意図的。下書きは揮発的なもので記録コストに見合わない

### 監査ログの実装形式（現時点では「思想」のみ確定）

実装方式（専用テーブル / トリガー / 既存 `ow_activities` 流用 等）は §5 の保留論点。  
本書では「**記録する**」という思想のみ確定とし、実装詳細は別途設計する。

### 5-1. 監査ログの実装方式と詳細度

  - 「公開した」「停止した」という事実のみ記録

**未定。実装時に詳細度とストレージコストのトレードオフを判断する。**

### 5-2. 企業への ADMIN 編集履歴の開示可否

ADMIN が `admin_seed` の行を修正した場合、その履歴を企業 admin に開示するかどうか。

- 開示する方向性: Opinio のミッション「Truth to Careers / 情報非対称縮小」と整合する
- 開示しない方向性: 運営の修正意図（修正理由）を含む場合の情報管理リスク
- どちらが正しいかはプロダクト判断。現時点では決めない。

### 5-3. ow_company_join_requests（migration 103）の再利用 vs 新設

migration 103 で作成された `ow_company_join_requests` テーブルは現在休眠状態。claim フロー実装時に：

- このテーブルを claim 申請テーブルとして再利用する
- claim 専用の新テーブルを別途作成する

**スキーマ詳細の精査と、既存コードへの影響確認後に判断する。**

### 5-4. 過去に却下した pull/request 型との関係

claim は企業が「既存の admin_seed 行に紐付く」pull 型。過去に設計上の理由で却下した push/request 型モデルとの関係性・差異を改めて整理する必要がある。

### 5-5. 判断②: 経歴の社名と企業マスタ claim の突合

- 求職者経歴の `company_text`（自由入力）を `company_id`（マスタ FK）に変換するかどうかの判断（判断②）
- 企業が自社マスタを claim した後、その企業に在籍していた求職者の経歴との突合をどう扱うか
- 「経歴 ≠ 権限」原則（確定済み）を維持しながら、社名の名寄せをどの粒度まで行うかの設計判断

**いずれも中長期の設計判断。Wantedly 型セルフサーブ / LinkedIn 型掲載の方向性と合わせて議論する。**
