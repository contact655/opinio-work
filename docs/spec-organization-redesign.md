# 組織体制機能 マスタ再設計仕様書

## 1. 背景

現在の ow_roles マスタ（29行・親子2階層）には以下の構造的問題がある：

- **MECE違反**：「営業」と「フィールドセールス」が同じ階層の選択肢として
  /profile/edit のドロップダウンに並んでいる。親と子が混在し、求職者が
  どちらを選ぶか判断に迷う
- **企業組織との乖離**：マスタが固定で、企業ごとの組織体制の違いを
  表現しきれない（例：「うちは EntFS と SMB FS で分けている」等）
- **抽象度のばらつき**：CxO 5職種（CEO/COO/CFO/CTO/CPO）と「フィールド
  セールス」が同じ階層に並ぶなど、粒度感が不揃い

## 2. 設計原則

**マスタは粗く、細部は role_title（フリーテキスト）で吸収する。**

- マスタ（ow_roles）= 検索・集計のための粗いラベル
- ow_experiences.role_title = 人間が読む細かい肩書（フリーテキスト）

この2層構造を徹底することで、マスタのMECE性を保ちつつ、企業の細かい
組織表現は role_title で吸収する。

## 3. 段階的アプローチ

- **第1段階（本仕様書の対象）**：マスタ再設計 + UI整理
- **第2段階（バックログ）**：企業カスタマイズ機能。企業ごとに小分類を
  独自定義できる機能（ow_company_custom_roles 等の中間テーブル追加）。
  本番ユーザーの声を見てから判断

## 6. UI仕様

### 6.1 求職者 /profile/edit のカテゴリ選択ドロップダウン

**仕様：子のみ選択可、子なし大分類は親が選択可**

```
[選択してください]
─ 経営・CxO ─       ← 選択可（子なし）
─ プロダクト ─      ← 見出し（選択不可）
    プロダクトマネージャー  ← 選択可
    PMM                     ← 選択可
─ 営業 ─            ← 見出し（選択不可）
    フィールドセールス
    インサイドセールス
─ エンジニア ─      ← 見出し（選択不可）
    バックエンド
    フロントエンド
    ...
─ デザイナー ─      ← 選択可（子なし）
─ マーケティング ─  ← 選択可（子なし）
    ...
```

- 親に子がある場合：親は見出し表示（選択不可）、子のみ選択可
- 親に子がない場合：親が選択可（カスタマーサクセス、マーケティング等）

### 6.2 企業 /biz/organization の組織体制カテゴリ追加

**仕様：親追加と子追加を排他制御**

- 親カテゴリを追加 → 配下の子カテゴリのチェックボックスをdisable
- 子カテゴリを追加 → 親カテゴリのチェックボックスをdisable

これにより /companies/[id] での二重見出し（「プロダクト > プロダクト
マネージャー」のような重複表示）を構造的に防ぐ。

### 6.3 1職歴あたりのカテゴリ選択数

**仕様：単数（現状維持）**

ow_experiences.role_category_id は単数カラム。1職歴に対して1カテゴリ
のみ選択。兼任は role_title で表現する（例：「CS兼マーケティング担当」）。

## 7. 表示ロジック仕様

### 7.1 /companies/[id] 現役社員セクションの集計ロジック

**仕様：企業が親カテゴリを追加した場合、配下の子カテゴリで職歴登録
された社員も親グループに集約表示する**

例：
- 企業Xが組織体制で「営業」（親）のみを追加
- 社員Aが職歴で「フィールドセールス」（子）を選択
- → 社員Aのカードは「営業」グループ内に表示される

これは現実装の `empsByCategory.get(cat.roleId)` （role_id 完全一致）
では実現できないため、新規実装が必要：

- 親カテゴリの場合、配下の子カテゴリのrole_idも含めて in 句で集計
- 子カテゴリの場合、現状通りそのrole_idでマッチ

### 7.2 B（企業設定）が0件の場合のfallback

現実装の「カテゴリなしフラット表示」fallback（page.tsx L1388）は維持。
新規企業がB設定する前に求職者ページを見られる親切UXとして残す。

## 8. データ移行戦略

**戦略：案Y（テストデータ中心のため、全データを「その他」に寄せる）**

現状確認：本番ユーザー実質ゼロ、テストデータのみで運用中。

### 移行手順

1. 新マスタ ow_roles を21項目で再構築（旧29項目を全削除→新規21項目を作成）
2. ow_experiences.role_category_id を全行「その他」のrole_idに更新
3. ow_company_employee_categories の全行を「その他」のrole_idに更新
   （UNIQUE制約があるため、企業ごとに「その他」が1行残るよう調整）
4. テストデータの再登録は手動で実施

**注意**：本番ユーザーが発生した後にマスタを変更する場合は、案X
（旧→新ID マッピング表を作成して一括UPDATE）を必須とする。

## 9. 実装計画（次回以降の作業）

### Phase 1：DBマスタ更新
- migration: ow_roles を21項目に再構築
- migration: ow_experiences と ow_company_employee_categories の
  既存データを「その他」に寄せる

### Phase 2：求職者UI（/profile/edit）
- CareerHistoryEditor のドロップダウンを「子のみ選択可」に変更
- 親カテゴリは見出し（disabled option）として表示
- 子なし大分類は親を選択可とする

### Phase 3：企業UI（/biz/organization）
- CategoriesEditor のチェックボックスに排他制御を追加
- 親追加時：配下の子をdisabled化
- 子追加時：親をdisabled化

### Phase 4：表示ロジック（/companies/[id]）
- CurrentEmployeesSection の集計ロジックを修正
- 親カテゴリの場合、配下の子のrole_idも含めて集計
- 既存の fallback（B未設定時のフラット表示）は維持

### Phase 5：テストデータ整備
- 既存テストアカウントの職歴カテゴリを手動で再登録
- 各テスト企業の組織体制を新マスタで再設定

## 10. リスクと未決事項

### リスク
- 既存テストデータ（180行の ow_company_employee_categories）が全部
  「その他」に寄せられるため、視覚的に各企業ページが「その他」だらけに
  なる期間が発生する。テスト時に違和感が出る可能性
- 親が子を内包する集計ロジックは新規実装。テストケースが必要
