## 1. 現状フロー全体

### ステップ構成（3ステップ）

| Step | id | 質問 | 選択肢数 | 必須/任意 | レイアウト |
|------|----|------|---------|---------|-----------|
| 1 | `job_type` | あなたの職種は？ | **17個** | 必須（スキップ不可） | 2列グリッド |
| 2 | `experience_years` | 社会人経験は何年ですか？ | 4個 | 必須（スキップ不可） | 1列 |
| 3 | `worry` | 今一番の悩みは？ | 6個 | 必須（スキップ不可） | 1列 |

> ※ CLAUDE.md に「5ステップ」と記載があるが、現コードの `STEPS` 配列は **3要素**のみ。
> 「5ステップ強制完走」という認識は過去の仕様との混同と思われる。

### 遷移ロジック

```
選択肢をクリック → select(value) 呼び出し
  └ step < 2 → setStep(s+1) → 次のステップへ
  └ step === 2（最終）→ Supabase に保存 → done=true → 完了画面
```

- **「前に戻る」**: step>0 のとき表示。setStep(s-1) で戻る。バリデーションなし
- **「後で設定する」**: **全ステップで常時表示**。クリックすると `onboarding_completed: true` をセットして `/companies`（または `?next=` 先）へ遷移。つまりスキップ機能は**すでに実装済み**

### 進捗表示

- 横並び線セグメント（`flex: 1` の div × 3本）
- 完了済み/現在: `var(--royal)` / 未着手: `var(--line)`
- `role="progressbar"` + aria属性あり（アクセシビリティ考慮済み）
- ステップ番号は「Step 1 / 3」テキストでカード内に表示

### 保存内容・リダイレクト

保存先: `ow_profiles` テーブル

| カラム | 値 |
|--------|---|
| `job_type` | 選択した文字列（例: "フィールドセールス"） |
| `experience_years` | 選択した文字列（例: "3〜5年"） |
| `worry` | 選択した文字列（例: "転職すべきか迷っている"） |
| `onboarding_completed` | `true` |

- upsert パターン: 既存レコードあり→UPDATE、なし→INSERT
- 完了後: `/api/roles` に `candidate` ロールを POST（best-effort）
- リダイレクト: `?next=` パラメータ優先、なければ `/companies`
- **完了画面が表示されサイレント遷移はしない**（完了画面でユーザー自身が次のリンクを選ぶ）

### 重要な不一致：オンボーディング vs プロフィール編集

オンボーディング（17個）とプロフィール編集・企業側フィルター（11個）で**選択肢が別物**。

`ProfileEditClient.tsx` と `CandidatesClient.tsx` の共通リスト:
```
フィールドセールス / インサイドセールス / カスタマーサクセス / マーケティング /
事業開発・BizDev / プロダクトマネージャー / エンジニア / デザイナー /
HR・人事 / 財務・経理 / その他
```

- **オンボーディングにあってプロフィール編集にない**: `経営・CxO`, `コーポレート`, `データサイエンティスト`, `バックエンド`, `フロントエンド`, `フルスタック`, `SRE/インフラ`, `iOS/Android`
- **プロフィール編集にあってオンボーディングにない**: `事業開発・BizDev`（オンボーディングは `事業開発`）, `HR・人事`, `財務・経理`

→ この不一致はオンボーディングで設定した `job_type` がプロフィール編集画面に正しく表示されない問題を起こしている（例: オンボーディングで「バックエンド」を選んでも、プロフィール編集の select に選択肢がないため表示されない）

### 値の形式

- DB保存形式: **文字列（string）** そのまま（例: `"フィールドセールス"`）
- ID変換なし、単一値（配列ではない）
- マッチングロジック（`matching.ts`）は `profile.job_type.toLowerCase()` でキーワード部分一致（cs / sales / marketing / bizdev）

## 3. カテゴリ分類案

### 前提: 分類の方向性

IT/SaaS特化プラットフォームとして、「プロダクトを売る人」「プロダクトを作る人」「プロダクトを支える人」という軸が直感的。

### 案A: 職能ライン軸（3カテゴリ）

| カテゴリ | 職種 | 選択肢数 |
|---------|------|---------|
| **ビジネス** | 経営・CxO / 事業開発 / フィールドセールス / インサイドセールス / カスタマーサクセス / マーケティング / コーポレート | 7 |
| **プロダクト・デザイン** | プロダクトマネージャー / デザイナー / データサイエンティスト | 3 |
| **エンジニアリング** | エンジニア / バックエンド / フロントエンド / フルスタック / SRE/インフラ / iOS/Android | 6 |
| その他 | その他 | 1 |

**評価**: ビジネスが7個と多い。2段階化の恩恵は「エンジニアリング」「ビジネス」で効く。「プロダクト・デザイン」は3個なのでそのまま表示でも可。

### 案B: SaaS職能軸（4カテゴリ）— **推奨**

| カテゴリ | 職種 | 選択肢数 |
|---------|------|---------|
| **セールス・CS** | フィールドセールス / インサイドセールス / カスタマーサクセス / 事業開発 | 4 |
| **マーケ・コーポレート** | マーケティング / コーポレート / 経営・CxO | 3 |
| **プロダクト・デザイン** | プロダクトマネージャー / デザイナー / データサイエンティスト | 3 |
| **エンジニア** | エンジニア / バックエンド / フロントエンド / フルスタック / SRE/インフラ / iOS/Android | 6 |
| その他 | その他 | 1 |

**評価**: SaaS業界の採用市場に近い括り。最大カテゴリが6個（エンジニア）で収まる。「セールス・CS」は求人数が多いため分かれて見つけやすい。

### 案C: スキル・レイヤー軸（3カテゴリ）

| カテゴリ | 職種 | 選択肢数 |
|---------|------|---------|
| **収益・グロース** | 経営・CxO / フィールドセールス / インサイドセールス / カスタマーサクセス / マーケティング / 事業開発 | 6 |
| **プロダクト・技術** | プロダクトマネージャー / デザイナー / データサイエンティスト / エンジニア / バックエンド / フロントエンド / フルスタック / SRE/インフラ / iOS/Android | 9 |
| **コーポレート** | コーポレート | 1 |
| その他 | その他 | 1 |

**評価**: 「プロダクト・技術」が9個と多くなるため2段階化の効果が薄い。不採用推奨。

### 結論: 案Bを推奨

カテゴリ4個×サブ最大6個は認知負荷の観点で妥当。SaaS採用市場の文脈と一致し、求職者が自分の職種を探しやすい。

## 4. スキップ機能の現状と実装ポイント

### 現状: スキップは「すでにある」

「後で設定する」ボタン（`OnboardingClient.tsx` L453–488）が事実上のスキップ。
クリックすると `onboarding_completed: true` を保存してリダイレクトする。

→ **技術的なスキップ機能は実装済み**。問題はUIの目立たなさのみ。

### OnboardingGuard との整合

`OnboardingGuard.tsx` は `onboarding_completed=false` のユーザーを `/onboarding` にリダイレクトする。「後で設定する」は `onboarding_completed: true` をセットするため、**スキップ後のリダイレクトループは発生しない**。

| アクション | onboarding_completed | Guard動作 |
|-----------|---------------------|---------|
| 全ステップ回答 | true | リダイレクトなし ✅ |
| 「後で設定する」 | true | リダイレクトなし ✅ |
| 途中で離脱（ブラウザ閉じ等） | false のまま | 次回アクセス時に `/onboarding` へ誘導 |

### 後から設定できる導線

`/profile/edit` の「希望条件」タブに `job_type`・`experience_years`（`desired_work_style`等）の設定UIがある。ただし選択肢がオンボーディングと不一致のため、オンボーディングでの設定値が正しく表示されない場合がある（前述の不一致問題）。

`worry` フィールドはプロフィール編集にも再設定UIがある（`/profile/edit` 希望条件タブ）。

### 途中保存の必要性

現状の「後で設定する」はステップ途中でも呼べるが、**途中まで選んだ回答は保存されない**。例えば Step 2 で「後で設定する」を押すと `job_type` の答えは捨てられる。

部分保存が必要かは設計判断次第:
- 「最初の質問だけ答えてスキップ」を許すなら保存ロジックを `select()` 内に毎ステップ組み込む
- ユーザーにとっては「後で全部やり直す」方が認知的に楽な可能性もある（状態管理の複雑化を避けるため）

## 5. 離脱ポイントの現状

### ①「後で設定する」ボタンの視認性

```
fontSize: 12, color: "var(--ink-mute)", background: "none",
border: "none", textDecoration: "underline",
textDecorationColor: "var(--line)"
```

- 文字が小さく（12px）・薄く（`--ink-mute`）・アンダーラインも薄い（`--line`色）
- 「前に戻る」ボタン（`border: "1px solid var(--line)"` あり）より視覚的に弱い
- 「後で設定する」に気づかず閉じてしまうユーザーがいる可能性が高い

### ②「前に戻る」ボタンの目立たなさ

Step 1 では表示されない（step > 0 の条件）。表示される Step 2・3 でも `fontSize: 12, color: "var(--ink-soft)"` と控えめ。

### ③ 完了後のリダイレクト（現状は問題なし）

完了後は「完了画面」を表示し、ユーザーが次のリンクを自分で選ぶ設計。「サイレント遷移」はすでに解消されている。

## 6. 最初に着手すべき変更（優先順位順）

### P0: 選択肢の不一致を修正する（必須・リスク低）

**問題**: オンボーディング17個とプロフィール編集11個が別物。保存した値が後で表示されない。
**対応**:
1. 共通定数 `JOB_TYPE_OPTIONS` を `src/lib/constants/jobTypes.ts` に切り出す
2. オンボーディング・プロフィール編集・CandidatesClient の3箇所を同定数で参照する
3. 統一する選択肢案（17個 + プロフィール側の3個を統合し最終リストを確定）

**影響範囲**: 3ファイル変更のみ。DBスキーマ変更なし。`matching.ts` は部分一致ロジックのため影響ほぼなし。
**リスク**: 低（既存ユーザーの保存値はそのまま有効）

---

### P1: 2段階選択 UI（案B）を実装する

**変更内容**: Step 1 の `options: string[]` を廃止し、カテゴリ→サブ選択の2段階 state に変更。

```
// 現状
step=0 → 17択ボタン → select("フィールドセールス")

// 変更後
step=0 → 4カテゴリボタン → カテゴリ選択
       → サブ選択画面（最大6択）→ select("フィールドセールス")
```

**State 変更**:
- `subStep: "category" | "sub"` を追加
- `selectedCategory: string | null` を追加
- STEPS[0] は category 画面 → sub 画面の2フェーズ扱い

**UIプログレスバー**: Step 1 のバーを分割するか、サブ選択中は「Step 1 / 3」のまま表示するか（後者が実装コスト低）

**影響範囲**: `OnboardingClient.tsx` のみ。DB保存値の形式変更なし。
**リスク**: 中（UI全体の state 設計が変わるため、UXテストが望ましい）

---

### P2: 「後で設定する」ボタンの視認性改善

**変更内容**: スタイルを小リンクから明示的なボタンに格上げ。

```
// 変更前（現状）
fontSize: 12, color: "var(--ink-mute)", underline

// 変更後（案）
border: "1px solid var(--line)", borderRadius: 8,
padding: "8px 20px", color: "var(--ink-soft)", fontSize: 13
```

**影響範囲**: `OnboardingClient.tsx` スタイルのみ。
**リスク**: 低

---

### 実装順序の推奨

```
P0（不一致修正）→ P2（スキップ視認性）→ P1（2段階選択）
```

P0 は P1 の前提（選択肢統一後に2段階分類を設計する）。P2 は独立しており最小リスクで先行できる。P1 は最も影響が大きく、実装後に実ユーザーのドロップ率を見て調整する余地を持たせる。
